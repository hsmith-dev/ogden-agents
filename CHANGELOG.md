# Changelog

Every release of the `ogden-agents` npm package. Since `2026.10.8-1`, each release is dated: `YYYY.M.D-N` (year, month and day as plain integers, a mandatory sequence number). Before that, versions followed [semantic versioning](https://semver.org/)'s major.minor.patch, with named milestones; those entries are kept below as history. How a release is made is in [RELEASING.md](RELEASING.md).

## 2026.10.8-1 — continuous, date-based releases

Starting with this release, Ogden Agents retires named milestone versions (`1.0.0`, `v1.1`, ...) in favor of continuous, date-stamped releases: no more batching features into a numbered milestone, each change ships in its own release as soon as it is ready.

- **New version format: `YYYY.M.D-N`.** A version is the release date as three plain integers (year, month, day) followed by a mandatory sequence number, for example `2026.10.7-1` for the first release on October 7, 2026, `2026.10.7-2` for a second release the same day, and `2026.10.8-1` for the first the next day. Month and day are never zero-padded (`2026.10.7`, not `2026.10.07`): npm and semver both forbid a leading zero in a numeric identifier, so a zero-padded date is not a valid version at all. The `-N` suffix is **never omitted**, not even on a day's first release: under semver precedence a bare version (no suffix) always outranks a suffixed one with the same core date, so if a release ever went out without `-N` while another release on the same date had one, the two could sort in the wrong order; always including `-N` avoids that trap. This is still a valid, strictly ordered semver string (confirmed against node's `semver` package), so every existing tool that compares versions keeps working.
- **One channel: `latest`.** Every release is "just the newest dated one," so the old two-step release-candidate-then-stable process (`-rc.1` to the npm `next` dist-tag, then the plain version to `latest`) is retired: a release always publishes straight to npm's `latest` dist-tag and is never marked a GitHub prerelease. The desktop app's separate `next` update channel is unaffected (it already tracks the highest version of any release, stable or not) and keeps working, but there is no longer a distinct prerelease track for it to follow.
- **`scripts/release-notes.mjs` and the Tag release workflow now validate this format**, not classic semver, and every release needs its own exact `CHANGELOG.md` section (there is no more falling back to a shared "stable" section for a release candidate, since there are no release candidates any more).
- See [RELEASING.md](RELEASING.md#releasing-going-forward-continuous-date-based-versions) for the current process; the version-numbered checklists further down are kept as release history and predate this change.

## 1.0.0 — every agent, unattended builds and a palette of your own

The first published release, cut through the release workflow described in [RELEASING.md](RELEASING.md). CI runs today's checks with fake agents; real-provider and real-OS live checks (real Claude Code/Antigravity/Codex/Grok sign-ins, real Windows/macOS/Linux machines, real Ollama/LM Studio) are tracked as outstanding evidence in [docs/v1-readiness.md](docs/v1-readiness.md) rather than claimed here.

- **Build with Codex, Grok or Antigravity, not only Claude Code.** When more than one agent can build, **Build this story** asks which, and each agent says in plain words how it would build here and why: **Builds on its own, and you review the result**, **Builds with you watching**, or **Not ready**. Your choice applies to that run. A project has a **Default build agent** in its Workspace settings (Automatic uses the project's default chat agent when it can build, else Claude Code), used when you pick none and by **Build all ready**. Every build keeps the same rules whatever the agent: Ogden Agents answers or you answer each request, files only inside the build's own copy, protected files never, no network for its commands, and a build that cannot be contained is refused, never run loose. **Codex** (your OpenAI API key) builds with you watching for now: its own sandbox has to be checked on a real computer before it can build on its own (RELEASING.md lists the checks). **Grok** (your xAI token) and **Antigravity** build with you watching only; Ogden Agents never uses Antigravity's modes that approve for you. An agent that hits a rejected key, an expired sign in or its usage limit ends the run blocked in its own words, with **Retry**, and after a usage limit **Build again with** another agent (a fresh copy). Nothing retries by itself, and no token or cost is stored. GitHub Copilot CLI is not part of this: GitHub's terms don't allow driving it in the background, so it stays an interactive terminal. Note: a project with no default build agent whose default chat agent is Codex, Grok or Antigravity now offers that agent first when you press Build.
- **Terminals: your agents' own command line programs, side by side (Developer mode).** A project's **Terminals** tab, shown only with Developer mode on, opens real terminals in tabs and splits: a plain shell, Claude Code, Codex, Grok, Antigravity, Copilot (interactive use only) and Gemini if you have it. Ogden Agents only detects these programs (never installs them) and you sign in inside each one yourself. Each terminal gets a small environment with no secret in it (proxies and SSH keys only if you opt in, Settings > Terminals), shows a guess of its status (working, idle, may need you, ended), and can notify you, opt in per terminal or per program, naming only the project and the terminal. Layout, names and opt ins survive a restart; terminals come back stopped with **Start**; what they printed is never stored. Up to 8 per project and 16 in all. Turning Developer mode off with terminals running asks whether to stop or keep them.
- **Watch every build, build all that is ready, and hear when one needs you.** In a project with Unattended builds on, a build session shows a run view: the ticket, the agent, the sandbox used, the time left before the run's limit, **Stop** while it runs, and, when it is blocked, the reason in plain words with **Show details** (the raw code, always open in Developer mode), **Retry**, and for an intent gap **Apply the saved fix and retry**. A **Runs** tab (`g r`) lists every run and the queue. The board has **Build this story** on every ready card (never on one that waits for another) and in the ticket's detail sheet, which also lists the ticket's runs, and **Build all ready** in its header. A run's checks are reported in full: each check's detail and the end of the test output in the run view and the review page, the failing check on the Runs tab, the board card and the detail sheet ("Build failed: 3 tests failed when re-run"), **Check again** after you fix it, and a **Test command** in a project's settings that replaces the one Ogden Agents finds. A blocked run and a run ready for review reach the **Needs you** group (with the count in the tab title, a polite announcement and, if you turned them on, a desktop notification and the chime) and, if you add one in Settings > Notifications, a **webhook**. A webhook is off until you add its address: it is kept in your computer's keychain and never shown again (the list shows only its domain), it gets a short message naming the project, the story and what happened (never code, a diff, a path or a secret), only for projects with builds on, with a 5 second limit, no redirect followed and the answer's size capped. Ogden Agents refuses an address that is not `https://` (or `http://` to this computer) and refuses link-local and cloud metadata addresses. **Send test** shows the HTTP result inline.
- **Retrospectives: look back on a finished epic.** Turn on **Retrospectives** in a project's BMad Method settings (it needs Board and the project's trust). Each epic on the Board then has **Look back on this epic**, and a finished epic (every ticket done or dropped) offers "Every ticket in this epic is done. Look back on it?" with **Look back** and **Not now** (Not now is kept). It opens an ordinary planning chat in which BMad Method's retrospective skill reads the epic's files and Ogden Agents' short build records of its runs (outcome, checks, why a build was blocked, how long; never a transcript) and writes `epic-<name>-retrospective.md` beside the epic. The Board shows its verdict (Accepted, Accepted with open items, Not accepted) and date as a chip, read from the file's header only. The retrospective's card in the chat offers **Add the lessons to AGENTS.md** and **Turn the action items into tickets**, each a chat you approve (the agent edits `AGENTS.md` and the tickets; Ogden Agents writes neither), and **Save the lessons for later builds**, which makes one local commit of `AGENTS.md` and the retrospective (only those, and only the ones that changed), never pushed, so every later build carries the lesson. Approve no longer stops for an unstaged, uncommitted `AGENTS.md` at the project's top folder. Nothing starts by itself, and a project with Retrospectives off, including every Simple project, shows and runs none of it.
- **A Local model: no account, no key, and its harness connects only to your own server.** Settings > Agents installs the Local model (OpenCode, about 45 to 62 MB, downloaded from its official releases into Ogden Agents' own data folder and checked against a pinned SHA-256; on Windows its search tool too) and lets you set up servers: a one-click preset, **Detect on this computer** (it looks only at `127.0.0.1` and `localhost` on two usual ports, only when you press it, and links the official download pages when nothing is found), or any OpenAI compatible address with an optional key. A server on this computer needs no confirmation; another host shows exactly where your messages, the files the model reads and your project's text will go, warns about plain http, and waits for your confirmation, asked again if the address changes. A key is kept in your computer's keychain, never shown again, never written to a file and passed only to that chat's process; changing a server's address removes its key. **Test connection** and **Show models** say in plain words whether the server is ready, running with no model loaded, not running or refusing the key, and list each model with the size, context length and tool support the server reports (nothing is guessed), a caution for small models and small contexts, and **Use for new chats**; a model the server drops is shown as missing and its chats are refused rather than switched. A Local model chat asks before every command or file change (**Ask** only), streams, continues after a restart, and says in plain words when the server stopped, the model is missing or the context is full, without waiting out the harness's minute of retries. Its chats are stored in plain text in the data folder (`agents/local-home`); Uninstall keeps them. Small local models follow tool instructions less reliably than hosted ones.
- **A notice when a newer version is out.** Each time Ogden Agents starts, the server asks GitHub Releases (not your browser) for this project's latest release and, unless Ogden was installed from GitHub Releases, npm for the public list of versions of `ogden-agents` too, and shows "Ogden 0.5.0 is available" with the command that updates (`npx ogden-agents@latest`, or `npm install -g ogden-agents@latest` for a global install, which Ogden never runs for you). On a stable version you hear about newer stable versions; on a release candidate or `next` you hear about both. Dismiss it and it stays hidden for that version in this browser. Each source gets one `GET` of a fixed address, with a 5 second limit, no redirects and a size cap: no version, account, project, path or token goes with it, and a failure is silent. Settings > About shows your version and channel, which sources it checks, when it last checked, a **Check now** button and a switch, **Check for new versions when Ogden starts** (on by default). `OGDEN_AGENTS_OFFLINE=1` stops every check.
- **Grok beside Claude Code, Antigravity and Codex.** Settings > Agents installs Grok (xAI's coding agent; about 200 MB into Ogden Agents' own data folder; its program is unpacked and checked against a pinned SHA-256, and npm's own launcher never runs) and takes your own xAI API access token, checked with xAI for free and kept in your computer's keychain. Grok is off until you add a token, and signing in with an account isn't supported here; the Grok card says so in every state. Grok runs a project's own settings, hooks and MCP servers, so a Grok chat starts only in a project you trusted (the same trust as the Board, asked again if those files change). It offers **Ask** and, in Developer mode, **Skip all** (never Auto), chosen when the chat starts and fixed after that. It asks through the same permission cards, continues after a restart, and runs BMad Method's skills from `.claude/skills` where Planning is on. The sidebar and notifications say an API key was rejected, instead of asking you to sign in again, for Codex and Grok chats.
- **Codex beside Claude Code and Antigravity.** Settings > Agents installs Codex (OpenAI's coding agent; about 400 MB into Ogden Agents' own data folder, checked against pinned hashes) and takes your own OpenAI API key, checked with OpenAI for free and kept in your computer's keychain. There is no sign in with a ChatGPT account, because OpenAI's terms don't allow other apps to use subscription sign in; the Codex card says so. A Codex chat asks through the same permission cards (Allow once, Deny), offers **Ask** and, in Developer mode, **Skip all** (never Auto), keeps its models, handoff and errors in plain words, continues after a restart, and gets BMad Method's skills in `.agents/skills` where Planning is on. Codex starts with its plugins download off and keeps your key in memory only, so no key is ever written to a file. Its own `.codex` folder joins the protected paths. The key reaches only Codex's process.
- **Continue a chat with another agent.** When a chat's agent runs out of usage (a plan or rate limit), the error says so and offers **Continue with another agent**; the chat's header menu offers it any time the chat is idle. Ogden Agents builds a summary of the chat itself (no model involved: the goal, the files changed, what was done, and the latest messages, with keys and tokens masked), shows which provider will receive it, and lets you edit it before anything is sent. The same chat then continues with the other agent behind a "Continued with" divider, keeping its permission mode when the new agent offers it (otherwise Ask). Switch back the same way later; the first agent picks up its own session.
- **Start Ogden by double-clicking.** The repository's `start/` folder, and every GitHub Release, has a start script for each OS: `Start Ogden.command` (macOS), `Start Ogden.cmd` (Windows) and `start-ogden.sh` (Linux). Each checks that Node.js 24 or later is installed and runs `npx ogden-agents@latest`, which opens Ogden Agents in the browser. Without Node.js it says how to install it and opens the Node.js download page; it never installs anything itself or asks for administrator rights. See [Start Ogden](README.md#start-ogden).
- **GitHub Releases.** Every version tag now creates a GitHub Release carrying the packed tarball, the start scripts, an install helper (`ogden-install.mjs`), `SHA256SUMS.txt` and these notes, even where npm publishing isn't set up (publishing to npm is now opt-in with the repository variable `NPM_PUBLISH=true`; see [RELEASING.md](RELEASING.md)). A manual run of the Release workflow is a dry run that builds the assets without releasing. The start scripts take `--github` (or `OGDEN_AGENTS_SOURCE=github`) to install and update from a release instead of npm: the tarball is checked against `SHA256SUMS.txt` before anything is installed, installs go to your own user folder, the previous version is kept for rollback, and a private repository needs `gh auth login` or `OGDEN_AGENTS_GITHUB_TOKEN`. `@ogden-agents/shared/release-source` is the shared "newest version" interface for this and for the newer-version notice.
- **A version bump on `main` is a release.** Merging a new version (the five manifests and a `CHANGELOG.md` section) to `main` tags it `v<version>` and starts the release workflow on the tag, with no hand-made tag; a version already tagged is left alone, and a bump whose manifests disagree or whose changelog section is missing fails before any tag is made. The release workflow itself is unchanged: a run on a tag is a release, a manual run on a branch is still a dry run. See [RELEASING.md](RELEASING.md#releasing-by-version-bump).
- **Choose a palette, or build your own.** Settings > Appearance offers the Ogden, Forest and Ember palettes (the same layout, typography and status colors, different hues) alongside **Build your own theme**: separate light and dark colors with a live contrast check (background, text and accent need at least 4.5:1) and JSON import/export. Your choice is saved in this browser and applied before first paint, so there is no flash of the wrong theme.
- **Shared MCP servers and reusable skills, from Settings.** Settings > MCP servers connects local commands or remote HTTP/SSE servers to coding agents across every project (changes apply the next time an agent session starts; local commands run on this computer); Settings > Skills keeps shared, named instruction snippets the same way. Both are validated before saving, and credentials (environment variables or request headers) are kept in the local SQLite database rather than your OS keychain, so only enter ones you trust this computer to keep.
- **Find Ogden's maker, or chip in for coffee.** The sidebar links to HarrisonSmith.AI for custom software and AI workflow services, and Settings > About has an optional Venmo coffee link; every feature of this free, MIT-licensed app works without paying anything.
- **Messages sent right away no longer race the agent's own events.** Fixed a bug where sending a second message immediately (or a provider that answers the steering acknowledgment and its next output in the same synchronous read) could misorder or cut off the injected message's reply.
- **README and sharing kit corrected to match the implementation.** Remaining real-machine evidence (real provider sign-ins, real OS installs, real local-model servers) is tracked, not claimed, in [docs/v1-readiness.md](docs/v1-readiness.md); desktop installers remain unsigned.

## 0.5.0 — Antigravity beside Claude Code

Published first as `0.5.0-rc.1` on the `next` dist-tag (`npx ogden-agents@next`), then as `0.5.0`. Each chat picks its agent: Claude Code, or Google's Antigravity, which Ogden Agents installs, signs into and runs for you. Both can chat at once, in any project.

- **Pick the agent for each chat.** A project's Chats page has an agent picker beside **New chat**. A chat keeps the agent it started with; the session header, the Chats list and the status sidebar name it. An agent that isn't installed or signed in stays in the picker, unavailable, with its reason and a link to Settings > Agents.
- **A default agent per project.** Workspace settings has **Default agent**: new chats in that project start with it, and every open tab follows at once. Welcome asks which agent you want when there is more than one, and that answer is the default for projects you add.
- **Antigravity, installed and signed into from the app.** Settings > Agents installs Antigravity's own ACP server for your computer (Macs with Apple silicon, and 64-bit Intel or AMD Linux and Windows) into Ogden Agents' data folder, checked against the SHA-256 this release pins; nothing is installed globally, and Uninstall removes it (it keeps your Antigravity chats and sign-in). Sign in with Google, or save a Gemini API key in your OS keychain. Google's Antigravity terms say that using it through apps Google doesn't make can get your Antigravity and Gemini CLI accounts suspended; the card says so before you sign in. A computer Google publishes no build for is told so, with no Install.
- **Antigravity chats.** Replies stream, its tool calls show, and it asks through the same permission cards (**Allow once** picks Antigravity's own allow-once option; Ogden Agents never picks its "always" options). It offers **Ask** and, in Developer mode, **Skip all**, never **Auto** (its own auto-edit mode would approve edits to protected files). Its chats continue after a restart. The Chat | Terminal toggle stays Claude Code's: Antigravity's says why it isn't offered. On Windows its first answer can take about 17 seconds; the chat says it is starting.
- **Protected paths for every agent.** Antigravity's own folders (`.gemini`, `.agents`) join `.claude`, `.git`, `_bmad` and the rest: an edit there always asks with a card.
- **BMad Method with Antigravity.** In a project with Planning on that uses Antigravity (its default agent, or one of its chats), setup also puts BMad Method's skills in `.agents/skills`, where Antigravity reads them, and a planning session can run with it. A Simple project gets nothing BMad Method from Ogden Agents, whichever agent it uses.
- **Keys reach only their own agent.** A saved key, or one in the environment Ogden Agents started in, reaches only that agent's own process. Every other process Ogden Agents starts (installers, the uv and BMad Method scripts, the process killer, the Start Menu shortcut, the browser opener) gets a short allowlisted environment with no keys or tokens at all, and a test fails the build if one ever inherits the whole environment.
- **Upgrading keeps everything.** Every chat stored before this version is a Claude Code chat, and Claude Code stays the default agent until you choose another.

## 0.4.0 — BMad Method per project, planning and the board, and permission modes

Published first as `0.4.0-rc.1` on the `next` dist-tag (`npx ogden-agents@next`), then as `0.4.0`. Each project chooses whether it uses BMad Method's features, and a project that doesn't stays a plain set of chats. A project with Planning on goes from an idea to a spec and a ticketed epic in chat, and Board shows its tickets live. Each chat also has a permission mode: Ask, Auto, or (in Developer mode) Skip all.

- **BMad Method, per project.** A project's settings have a BMad Method section: a main switch, **Use BMad Method in this project**, and one switch per feature (Planning, Board, Unattended builds, Retrospectives). This version ships Planning and Board; Unattended builds and Retrospectives are greyed and marked **Coming soon**. A feature that needs another turns it on too, and turning one off turns off what needs it, with a line saying what changed. The choice is kept across restarts and shows at once in every open tab, and turning a feature off never removes your BMad files. A feature that is off can't be used: the server refuses it.
- **Simple projects stay simple.** With every feature off, a project shows only its Chats, its chats start Claude Code with nothing BMad Method from Ogden Agents (no extra tools, instructions or settings), and nothing is written into the project's folder. Claude Code still loads the project's own skills, `CLAUDE.md` and settings, as it does in a terminal. Developer mode's Chat | Terminal toggle works as before.
- **Projects that already use BMad Method.** A project whose folder already has BMad Method's files (`_bmad/`) offers its features once on its chats page: **Choose features** opens its BMad Method settings, and **Not now** hides the offer for good. Looking for the files reads the folder and never changes it.
- **Set up BMad Method from the app.** Turning Planning or Board on in a project without BMad Method (or **Set up** on its Plan or Board page) sets it up with no terminal: a list of steps, plain errors, and "Ready to plan." at the end. A chat still opens if setup fails.
- **BMad Method, pinned and downloaded when you ask.** The package no longer ships copies of BMad Method. Each release pins Ogden Agents' maintained fork of BMad Method (`hsmith-dev/BMAD-METHOD`: upstream `bmad-code-org/BMAD-METHOD` plus Ogden Agents' small patches, see [docs/bmad-fork.md](docs/bmad-fork.md)) to one commit and a content hash. Set up, or the Board's **Download BMad Method**, downloads the pinned version once, checks it against that hash before anything is saved, and keeps it in Ogden Agents' data folder; setup and the Board run BMad Method's scripts only from that checked copy, never a project's own. Nothing downloads on startup or when a page loads, and offline the download says so plainly. After an upgrade that moves the pin, it asks to download again.
- **Trust once per project, for the scripts you allowed.** The first time a feature that runs the project's own BMad Method scripts is turned on (Board), Ogden Agents says so and asks to confirm; until then nothing of the project's runs. The trust holds for those scripts as they were: if anything changes them afterwards, the Board runs nothing and asks again ("This project's BMad Method scripts changed. Run them?"). Each run uses a private copy of the scripts made from exactly what was checked, so a change landing during a run never runs. Ogden Agents' own setup and Upgrade keep it. The scripts always run without your API keys or other secrets, and Ogden Agents never writes Python's cache into the project.
- **Plan.** The Plan tab (`g p`) lists every BMad Method skill and module installed in the project, in plain words and groups (Developer mode adds each skill's name), with **Start from an idea** first; a module installed later shows up on the next visit, marked **New** for a week. Each action starts a planning session: an ordinary Claude Code chat with the skill started for you.
- **Document cards.** When a planning session writes a BMad Method document, the chat shows a card with **Open** (the document, read-only, in a side sheet) and the next step as a button, such as **Turn this spec into tickets**, which starts the next planning session on it.
- **Board.** The Board tab (`g b`) shows the project's tickets by epic in status columns (Draft, Ready, In progress, In review, Built, Done, Blocked), with "Waits for" and blocked reasons, and a ticket's details in a side sheet. A status an agent writes shows within seconds, the card highlighted. A card's menu moves a ticket (Move to Ready, say), written into its plan file through BMad Method's own `tickets.py`; Ogden Agents never sets Done, and moving a ticket out of Done asks "Reopen this ticket?" first. There is no drag in this version.
- **Reduced mode.** A project whose BMad Method lacks what a page needs (an older or plain upstream install) says so on that page in one sentence, with **Upgrade this project**, which adds what is missing and never replaces the project's own skills.
- **New projects start Simple, or as you choose.** Settings > New projects sets what a project you add starts with: Simple chats (every BMad Method feature off, the default) or BMad Method with the features you pick (those this version ships). Welcome asks "Simple chats or BMad Method?" once for your first project; the answer sets only that project. Projects you already have are never changed, and nothing is written into a project's folder.
- **Permission modes, per chat.** A chat's header has a mode picker. **Ask** (where every chat starts, also after a restart) is the permission cards as before. **Auto** lets Claude Code's own auto mode approve safe actions and ask about the rest through the cards; edits to protected paths (`.git`, `.claude`, `.vscode`, `.idea`, BMad Method's `_bmad` and the like) still ask. **Skip all** runs Claude Code with its permission checks skipped: it is offered only in Developer mode, which the server keeps and enforces, needs a red confirmation, and shows a red banner with a way back to Ask; turning Developer mode off puts every Skip-all chat back in Ask. A mode the agent switches to by itself never sticks.
- **Upgrading from 0.2.0 or 0.3.0 keeps everything.** Every project, chat, caution level and Always allow rule stays as it was, every project opens as Simple chats, every chat is in Ask, and Welcome doesn't ask its new question. A project whose folder already has BMad Method files offers its features once on its chats page, and its BMad Method settings say so and name the default for new projects.

## 0.3.0 — the agent's own terminal

Published first as `0.3.0-rc.1` on the `next` dist-tag (`npx ogden-agents@next`), then as `0.3.0`. For advanced users: switch a chat to Claude Code's own terminal and back, on the same session.

- **Chat | Terminal toggle, in Developer mode.** With Developer mode on (Settings > Appearance), a Claude Code chat's header has a **Chat | Terminal** toggle (or `⌘.` / `Ctrl+.`). The terminal runs `claude --resume` on the chat's own session, in the project folder, in a terminal the server owns, shown in the browser. Only one of them drives at a time: while the terminal drives, the chat is read-only (the server refuses chat messages too), and the conversation can be read beside the terminal.
- **Terminal messages come back to the chat.** On switching back, what you sent in the terminal and Claude Code's replies appear in the chat, yours marked "from terminal", and the next chat message continues the same session.
- **The terminal keeps running.** Closing or reloading the tab doesn't stop it: reopening the chat reattaches, with the recent output. Several tabs can watch and type, and the size follows the tab that typed or resized last. The connection reconnects by itself after a drop.
- **Never stuck.** The toggle switches only while the chat is idle. If the terminal's `claude` exits (`/exit`, a crash), the chat drives again; after a server restart, a chat left in the terminal is back in the chat, resumable.
- **Clear reasons where it can't work.** The toggle is disabled with a plain reason when the agent can't resume its session in its own terminal, when the terminal module (`node-pty`) can't load on this computer (the app still runs), or when Claude Code's CLI can't be found.
- **macOS, Windows and Linux.** On Windows the terminal runs through ConPTY, and an npm-installed `claude.cmd` resolves to its own `claude.exe`.
- **Security.** The terminal has its own WebSocket per session, behind the same gate as every other request (`Host`, the tab's token, `Origin`). What passes through the terminal is never written to the event log, the database or the logs; the CLI gets the same environment and credentials as the chat's agent.

## 0.2.0 — chat and workspaces

The first real release on npm (`0.0.0` was a name reservation), published first as `0.2.0-rc.1` on the `next` dist-tag (`npx ogden-agents@next`), then as `0.2.0`. It includes everything listed under 0.1.0, which was never published. Ogden Agents now runs Claude Code: chat with it in your projects, answer its permission requests, and pick up where you left off after a restart. Run it with `npx ogden-agents` (Node 24 or later on macOS, Windows or Linux).

- **Workspaces.** Add a project by browsing to its folder, or start a new project folder, and switch between projects from the sidebar header. Each project has its list of chats with **New chat**, and a settings page where you can delete its history (refused while an agent is working or waiting in it).
- **Chats with Claude Code.** Replies stream in as the agent writes them. A message sent while the agent works is shown as **Queued** and sent after the reply; **Stop** ends a turn, and whatever was queued comes back to the composer. The agent's reads, edits and commands show as tool-call rows, grouped in Comfortable density, with the diff of each edit. An error shows its reason with **Try again**, and an agent that has gone quiet gets a check-in line with Stop. Long chats open at their latest page, with **Show earlier** and **Jump to latest**.
- **Chats that persist and resume.** Every chat is kept in the event log. After a restart (or an agent crash) the next message reopens the agent's own session, so the chat keeps its context; where the agent can't resume, it starts again primed with the chat's transcript.
- **Permission cards and caution levels.** Nothing the agent asks for runs until you answer its card: **Allow once**, **Always allow** (for that command prefix or path, in that project), or **Deny** with an optional reason, which goes to the agent. Each project has a caution level (**Ask every time**, the default; **Ask for commands**; or **Ask only for risky actions**) and a list of its Always allow rules, each with Remove.
- **Status sidebar and Needs you.** The sidebar shows every project's chats with their live state (working, waiting, idle, error), and **Needs you** lists every request waiting on you, in any project, with a count in the tab title and screen reader announcements.
- **App shortcut.** With per-tab sign-in, a bookmark can't reopen the app, so Ogden Agents can add a shortcut to your OS app menu (offered on first run, and in Settings > Appearance) that opens a fresh, signed-in tab.
- **Per-tab token hardening.** API and WebSocket access use only the per-tab bearer token described under 0.1.0, never a cookie, so other web servers on your computer never receive anything they could replay. Event subscriptions are windowed per project, so a page load no longer replays the whole history.
- **Sign in with your Claude subscription.** Settings > Agents has a Claude Code card that signs you in to your Claude subscription from the browser, with no terminal.
- **Or use an API key.** **Use an API key instead** checks an Anthropic API key and keeps it in your OS keychain; it is used only while no subscription is signed in, and never shown again (just its last four characters) until **Remove key**. When Claude Code's sign-in check is slow or fails, the last sign-in state it confirmed in the past 5 minutes is used; with none, the key stays out of use.
- **Install Claude Code from the UI.** The package doesn't bundle Claude Code. The Claude Code card detects it and, with **Install**, installs a pinned, integrity-checked copy into Ogden Agents' data folder, with progress on the card.
- **Sign in again from a chat.** When Claude Code's sign-in expires, the chat's error offers **Sign in** (or a link to the API key when the key was refused), and **Try again** resends once you're signed in, keeping the chat's context.
- **Welcome on first run.** A first launch opens Welcome: set up Claude Code (install it, sign in or use an API key; it moves on by itself once ready), add your first project, and take or decline the app shortcut once, ending in that project's chats. **Skip for now** ends it for good, and Settings > Welcome brings it back. A data folder that already has projects skips it.
- **Reliability fixes.** Stopping a sign-in, an agent or the server ends its whole process tree the same way on every OS, with no stray console message on Windows; saving or removing an API key twice at once can't leave the wrong one in use; an answer to the shortcut offer that fails to send is retried; and signing in again resends only the chat it was started from, once.

## 0.1.0 — first build (not published)

Never published to npm: everything below first ships in 0.2.0. It was the foundation, not yet a working agent UI: it starts, signs you in and shows the app shell, but runs no agents.

- **Launcher and background server.** `npx ogden-agents` starts a local server on `127.0.0.1` in the background, or finds the one already running, and opens the browser with a one-time sign-in link. The server keeps running after the terminal closes, until Quit in the app. The launcher and server compare versions: an older server with no busy session restarts on the new version, and one with busy sessions keeps running until they finish. An open tab whose version differs from the server's shows a reload banner.
- **Security gate, per-tab sign-in, no cookie.** Every HTTP and WebSocket request passes one gate with `Host` and `Origin` checks. The launcher opens `/#c=<one-time code>`; the page removes the code from the address bar and exchanges it in a same-origin `POST` for a per-tab bearer token, kept in memory and the tab's `sessionStorage`. The token never appears in a URL or browser history, and no cookie is set, so other web servers on your computer never receive it. A bookmark or brand-new tab shows "Open Ogden Agents"; **New tab** in the sidebar opens another connected tab.
- **Content-Security-Policy.** The app runs only its own scripts: no inline script and no third-party origins.
- **Event log.** State reaches the UI through one append-only event log in SQLite, in the per-user data folder, over one WebSocket.
- **App shell.** The design system (light and dark themes, density) and the app layout with the workspace switcher and status sidebar, in their empty states.
- **Python tools, installed for you.** Settings > Tools checks for `uv` (the tool BMad Method's scripts run on) and, with one click, installs a private copy: the official release for your OS and CPU, verified against pinned hashes, with no terminal and no system changes.
- **Bundled forks.** The package ships pinned copies of the BMAD-METHOD and bmad-loop forks, locked by `forks.lock`.
- **Release pipeline.** Tagged releases publish from GitHub Actions through npm trusted publishing, only after the full test matrix passes, and then run `npx ogden-agents@<version>` from the registry on macOS, Windows and Linux.
