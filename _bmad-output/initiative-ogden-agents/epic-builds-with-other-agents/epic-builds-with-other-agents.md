# Build unattended with Codex, Grok or Antigravity, not only Claude Code

## Description

The user decided on 2026-10-05 to bring unattended builds with Codex, Grok and Antigravity into version 1, which pulls the relevant part of epic 8's V4 (v2) forward. Epic 5 built unattended builds for Claude Code: a ticket is built by `bmad-build-auto` in an Ogden-managed ACP session in its own worktree under `<data>/w/<run8>`, Ogden answers every permission request by rule (a file edit only inside the worktree and outside the protected paths, plus the git paths a commit needs; everything else rejected), commands run in the agent's sandbox with no network, the build is refused when no sandbox can hold it (fail closed), the agent's settings are locked, Approve merges the exact reviewed revision locally and never pushes. Story 5.3 already made the run's agent any registered agent id (`Run.agent`, null for old runs; a start request's `agent` is optional and defaults to the runner's agent). What is still Claude Code only is everything behind it: the one `BuildRunnerPort` (`createAcpBuildRunner`, `agent: 'claude-code'`), the sandbox chain (Claude Code's own Seatbelt or bubblewrap settings), the Claude Code sandbox and locked-settings quirk (`AcpAgentQuirks.sessionMeta`), and the Build dialog, which opens only when no sandbox exists and has "Use another agent" disabled.

This epic makes the build session agent-neutral and adds three agents, each only if it can be driven safely:

- Codex (OpenAI API key only, no sign-in; its own sandbox mode and approval policy set by config at start).
- Grok (xAI API access token only, no sign-in; its mode is set once in the `_meta` of `session/new`, and its folder-trust-off and always-approve switches are never used).
- Antigravity (Google sign-in or Gemini API key, as in chat; its modes are Ask and Skip all, its `auto_edit` approves protected files, so Ogden answers every card itself and never uses Skip all).

GitHub Copilot CLI is not included: the user's own terms note says autonomous background Copilot CLI use violates GitHub's terms, so Copilot stays interactive in epic 16's terminal. Local-model and OpenCode builds are out of scope (epic 14 chats only). Gemini CLI builds stay v2.

A spike (entry 1) decides first, per agent, whether Ogden can run a headless build session over ACP with rule-based permission answering and a sandbox. An agent that cannot be driven safely is reported as no-go with evidence; no frozen safety rule is weakened to make an agent fit (protected paths, no network in the sandbox, fail closed with no sandbox).

## Outcome

In a project with Unattended builds on, the user opens Build on a ticket, picks which agent builds it (or leaves the project's default build agent), and the run behaves as a Claude Code run does: it streams read-only, is stopped by the same limits, is verified by core, and is reviewed and approved the same way. A build with an agent that cannot be contained on this computer is refused with a plain reason and the Build dialog's choices, never run unsandboxed. A failure the agent reports in its own words (a rejected key, a usage limit, an expired sign-in) shows a plain reason for that agent and a Retry. The demo: two tickets build at once in one project, one by Claude Code and one by Codex (a fake agent in CI, a real one in the user's live check), each in its own worktree, and both are approved.

- E17-R1: The build session is agent-neutral. `BuildRunnerPort` has one implementation per agent id found through a registry (the agent's skill invocation syntax and its halt wording live in that agent's runner or quirk, AD-12), core names no agent, and the run's session `agentId` is the run's agent, not a constant. Starting a build with an agent that has no build runner refuses with a plain reason. Existing Claude Code runs behave exactly as before (their tests pass unchanged). (CAP-15, CAP-8; AD-1, AD-5, AD-12)
- E17-R2: Permission answering stays Ogden's, by the same rule for every agent (an attended-only agent, E17-R11, has every request a card at Ask instead). Core's policy (`build-permission-policy.ts`) is the only decider: an edit or write is allowed only when every path, normalized, is inside the run's worktree and outside the protected paths, or is inside the git paths a commit needs (never `.git/hooks` or `.git/config`); a shell command is allowed only because the agent's sandbox contains it; everything else is rejected. There is no card in an unattended build. An agent's own approval switches that skip a decision (Skip all, yolo, always-approve, `agent-full-access`, `danger-full-access`, `--dangerously-skip-permissions`, `autoMode`, folder-trust-off) are never set for a build session, and a request that arrives in a mode that asks less than the mode core set is refused and the run stops. Each agent's tool-path fields (`toolInputPaths`) and option kinds are read through its quirks so the one policy sees the real paths. (CAP-8, CAP-4; AD-4, AD-17, AD-18; user decision 2026-10-04 on the permission policy)
- E17-R3: Fail closed per agent. A build session needs a verified sandbox quirk for its agent: how that agent's own sandbox is turned on for the session, with only the run's writable roots writable, the protected paths and `.git/hooks` and `.git/config` denied, the credential folders and Ogden's data folder unreadable, and no network for its commands. An agent with no such quirk, or on an OS where its sandbox is missing or blocked, refuses to start a build session (`sandbox_unavailable` with the agent's own plain words; the existing check). Docker is not a build sandbox until its own decision (deferred-work, epic 5), so it changes nothing here. The agent's own settings and hooks are locked for the session the way Claude Code's are (5.6): the user's or the project's agent config cannot loosen the mode, the sandbox or the approval policy. (CAP-8; AD-17, AD-16; spec Constraints "Unattended runs are always sandboxed")
- E17-R4: Per agent, how the sandbox and mode are given is that agent's own, found by the spike and kept in its adapter. Codex: a sandbox mode and approval policy given at start (the adapter reads `INITIAL_AGENT_MODE` from its process environment and sends each mode's sandbox policy with every turn, so the spike checks whether `workspace-write`, with the run's roots as session `additionalDirectories` and network off, is reachable that way and where `.git` stays writable for a commit) (the spike records whether `workspace-write` with named writable roots and network off, and an approval policy that asks for what the sandbox would refuse, reach the ACP session, and whether the adapter's `read-only` start mode and fixed `INITIAL_AGENT_MODE` can carry them). Grok: no session modes; the build's mode goes once in the `_meta` of `session/new`, `resume` and `load` (`yoloMode` false and `autoMode` false, explicit); Grok's own sandbox (Seatbelt on macOS, Landlock on Linux, none on Windows) is used only if the spike shows it can be given the run's roots and no network through config. Antigravity: Ask and Skip all only; Ogden answers every card itself and never selects or starts Skip all or `auto_edit`; a sandbox is needed and none is recorded, so a build is unattended only if the spike finds one. (CAP-8, CAP-4; AD-17; agent-matrix.md rows)
- E17-R5: The run's contract is agent-neutral and unchanged: `bmad-build-auto ticket <ref>` in the worktree, the plan's status and blocked fields written by the skill, the per-run JSON result and activity NDJSON in the run's folder, Ogden's own `plan_checkpoint` and `done_checkpoint` pauses, the halt mapping to blocked codes, the test re-run, the diff check and the review. Each agent only differs in how the skill is invoked (its `skillInvocation`) and whether `bmad-build-auto` and its skills are found in the worktree (Codex through `.agents/skills`, Grok through `.claude/skills` and `/skill`, Antigravity through its skills folder, each already placed by the chat epics; a worktree has only committed files, so the spike checks what reaches it). If a skill cannot reach an agent in a worktree, the build is refused with a plain reason naming the missing skill, never run without it. (CAP-8, CAP-9, CAP-10, CAP-12; AD-12, AD-21; bmad-integration.md)
- E17-R6: The agent process gets only the environment allowlist and its own key as for chat (AD-16): Codex's `CODEX_API_KEY` and Grok's `XAI_API_KEY` reach only that agent's process, in memory, never a file in the worktree, the run's folder, the database, events or logs; Antigravity's sign-in is the one chat already keeps. Codex and Grok stay API-key only (no subscription sign-in is offered or used for a build); only Claude Code and Antigravity use a subscription sign-in. Each agent's home folder (`CODEX_HOME`, `GROK_HOME`) stays the chat's, under the data folder (a build writes no config into it that carries a key), and a build never reads the user's own `~/.codex`, `~/.grok` or `~/.gemini`. A build's commands cannot read the key or the home folder (denied reads). (CAP-16, CAP-8; AD-16, AD-17)
- E17-R7: Choosing the agent. The Build dialog gains an agent picker listing the agents that are set up and can build here now, with each unavailable agent shown with its plain reason (not set up, no sandbox on this computer, no key); the choice applies to that run only. A project has a default build agent in Workspace settings (`defaultBuildAgentId`, falling back, when unset, to the project's default chat agent if it can build, else Claude Code). The Build dialog opens from a card's Build when more than one agent can build, or on a refusal; with one choice, Build behaves as it does now. "Use another agent" in the sandbox-unavailable dialog is enabled and lists the agents that can build here. Retry keeps the run's agent and offers "Build with another agent" after a usage limit. Build all ready uses the project's default build agent. (CAP-15, CAP-8, CAP-19; AD-8; EXPERIENCE.md Build actions, Sandbox unavailable, Workspace settings)
- E17-R8: Failures use the agent's words, in plain language. Each agent that can build lists how it says: a rejected key, a usage or quota limit (its `usageLimitPatterns`), a sign-in that expired (Antigravity), a model that does not exist, a sandbox that failed to start. A run ends `blocked` with a plain reason for that agent (for example "Codex says the OpenAI key was rejected. Check it in Settings, Agents, then press Retry."), never the agent's raw error text in the UI or the logs, and Retry resumes from the plan's status. A usage limit never retries by itself; an auth failure never loops. No count of tokens or cost is stored (AD-8). (CAP-9, CAP-16, CAP-15; AD-8, AD-17)
- E17-R9: Limits stay shared. The per-project limit (2), per-install limit (3) and the 45 minute maximum run time apply across all agents together; a build with any agent is stopped by `killProcessTree` as before, and a crash or restart marks it `blocked` "interrupted". An agent that leaves processes outside its process group is the existing deferred-work item and is not widened by this epic. (CAP-8, CAP-9; AD-3, AD-17)
- E17-R10: Tests use fakes. Every test runs a fake ACP build agent personality per agent (Codex, Grok and Antigravity shapes: their permission option kinds, modes, tool-path fields, auth and usage-limit error words, a halt, a result file), a fake sandbox and the memory ports; none runs a real agent, the real keychain, the real network or reads `~/.claude`, `~/.codex`, `~/.gemini` or `~/.grok`. A table-driven conformance suite runs the same safety cases for every build-capable agent (an edit in a protected path is rejected, an edit outside the worktree is rejected, a request for a mode that asks less is refused, no sandbox means refused, the child environment is the allowlist with only that agent's key, a halt maps to its code, the result file is read, usage limit and rejected key give their words). Real-agent behaviour is the user's live checks. (CAP-8, CAP-15; AD-16, AD-17)
- E17-R11: Windows and the other OSes. Builds work wherever the agent's sandbox does: macOS (Seatbelt) and Linux and WSL2 (bubblewrap or Landlock as the agent supports) for each agent that proves it, native Windows only where the agent has a sandbox (Codex has a restricted-token sandbox; Grok none; Antigravity none recorded), otherwise the attended path (every request a card at the Ask level, which each agent offers) as for Claude Code. OS-sensitive parts are probed in CI on all three OSes with the fake personalities before being built (epic 3 retro A8, L2), and the real agents' sandboxes are the user's live checks. (CAP-8, CAP-1; AD-17, AD-21; agent-matrix.md)

## Done when

1. The spike's result is recorded, and the user has said, per agent (Codex, Grok, Antigravity), no-go, go for unattended builds (a verified sandbox), or go for attended builds only (no sandbox found: every request answered by Ogden at the Ask level, never unsandboxed unattended). An agent that is a no-go stops its entries and is reported with evidence; the epic ships with the agents that are go.
2. For each agent that is go for unattended builds, in a project with Unattended builds on, a ticket built from its card runs in its own worktree through that agent's session with Ogden answering every request by rule, is verified by core, and is approved or rejected as a Claude Code build is; an edit in a protected path or outside the worktree is rejected, a build with no sandbox is refused, and the run's child has only the environment allowlist and that agent's own key; an agent that is go for attended builds only builds with Ogden answering every request at the Ask level and its unattended path refused (CAP-8, CAP-10, CAP-12; E17-R1 to E17-R6).
3. The Build dialog shows the agent picker with each unavailable agent's reason, a project has a default build agent, and Retry keeps the agent and offers another after a usage limit (CAP-15, CAP-8; E17-R7, E17-R8).
4. The conformance suite passes for every go agent and for Claude Code on macOS, Windows and Linux with fake personalities, and Claude Code builds are unchanged (CAP-8, CAP-15; E17-R9 to E17-R11).
5. The epic's end-to-end suite passes on all three OSes and it is released in an `ogden-agents` v1.x npm version; the user's live checks with real agents are recorded (E17-R11).
