# Ogden as its own desktop app on macOS, Windows and Linux

## Description

The user asked for Ogden Agents as its own desktop app (user, 2026-10-04). It is a Tauri v2 app for each platform: a `.dmg` on macOS, an installer on Windows (NSIS, plus MSI where it builds), and an AppImage and a `.deb` on Linux. The app has its own window, a Dock or taskbar icon and an app menu. Ogden's local server runs inside the app on a Node runtime the app bundles, so the user installs nothing else. The npm route (`npx ogden-agents`) stays beside it, and both share one data folder.

The app does not change what Ogden is. The server, the web UI and AD-15's gate stay as they are. The Tauri shell starts the server as a sidecar and opens its window on the one-time code URL, the same way the launcher opens a browser tab today. The webview gets no Tauri IPC, so the page is exactly what a browser tab sees. The app updates itself (user, 2026-10-04: "we need a way to automate the updates of this app"). It uses Tauri's updater with signed update manifests published as GitHub Release assets, on a stable channel and a next channel that match npm's `latest` and `next` dist-tags. npm users get a light "a newer version is available" notice in the web UI. The first builds are unsigned and come with clear "how to open" steps. Code signing and notarization have slots in the pipeline for later, when the user has the Apple Developer account and the Windows certificate. A spike on all three OSes ends with the user's go or no-go before anything else is built.

## Outcome

A non-developer downloads one file for their OS, opens Ogden Agents like any other app, and reaches a first chat with no terminal and no Node install. Later versions arrive through an in-app "Restart to update" prompt that never interrupts running work. CAP-1's success signal is the measure, met through the app as well as through `npx ogden-agents`. The demo: on a fresh Mac, Windows PC and Linux machine, download the app, open it, sign in, chat, quit it (the server and agents stop), then open it again and update it from version N to N+1 on the next channel, with the chat still there.

- E13-R1: Ogden Agents ships as a Tauri v2 app on each OS and architecture: macOS on Apple silicon and Intel (one universal `.dmg`), Windows on x64 and ARM64 (an NSIS installer, plus MSI where WiX builds it), and Linux on x64 and ARM64 (an AppImage and a `.deb`). Each has its own window, a Dock or taskbar icon, and an app menu with About, Check for updates and Quit. (CAP-1, CAP-20; AD-3, AD-21)
- E13-R2: The app bundles everything the server needs. That is an official Node.js binary (the LTS line Ogden supports, pinned by version and SHA-256 for each OS and architecture, checked at build) as Tauri's sidecar, the npm that ships with it where `findNpmCli` finds it (agent installs need it), and the packed `ogden-agents` server with its production `node_modules`, native modules built for that target, as app resources. The user installs nothing else. The app ships node-pty on every target, because hidden-PTY sign-in (9.1) and the terminal toggle need it; AD-19 still lets the server run without it. The npm package is unchanged. (CAP-1, CAP-20; AD-19, AD-21, Stack)
- E13-R3: AD-15 holds unchanged inside the webview. The shell gets a launch URL from `/launcher/hello?launch=1` with the launcher token, and opens its window on `http://127.0.0.1:<port>/#c=<code>`. The webview's origin is the server's own, so the Host, Origin, per-tab token and WebSocket checks apply as in a browser. The shell grants no Tauri IPC or capability to that origin. Navigation away from the server's origin is blocked, and external links open in the system browser. The server's CSP is kept, and the app loads no remote content. (CAP-20; AD-15, AD-16)
- E13-R4: The app manages its own lifecycle. A second launch focuses the running window. Quitting the app stops the server and every agent cleanly: a busy-session confirmation, then the server's quit, then a process-tree kill as a fallback. On Windows a job object stops the whole tree, and the server exits if the shell disappears. Quitting stops only a server the app started. When a server started by `npx ogden-agents` is already running on the same data folder, the app attaches to it or restarts it through the AD-20 handshake, never stops running sessions itself, and leaves it running when the app quits. (CAP-1, CAP-20; AD-3, AD-20)
- E13-R5: The app and the npm route share the data folder at the location `dataDirPath()` gives today, unchanged. Data-folder migrations run on the first start of a new version. The database is copied to a backup first, a newer database than the running version is refused with a plain message, and the existing upgrade tests cover app-to-app and npm-to-app upgrades. (CAP-1, CAP-20; AD-5)
- E13-R6: The app updates itself. Only on start (no periodic checks), Tauri's updater checks a signed `latest.json` for the user's channel (stable or next, matching npm's `latest` and `next`). It downloads the update and verifies its signature and SHA-256 before installing. It shows "Update available — Restart to update" in the web UI through the server, never through IPC. It never restarts while an agent turn or a build is running, and it warns about running builds. A failed install keeps the old version. Linux `.deb` installs, which the updater cannot replace, get a notice with the download link instead. The updater signing key is the user's own: it is separate from Apple and Windows code signing and kept only as a GitHub Actions secret. (CAP-20; AD-20, AD-16)
- E13-R7: npm users see a light "a newer version is available" notice in the web UI when the npm registry has a newer version on their dist-tag. The notice shows the command or shortcut that updates, and can be turned off in Settings. No other data is sent, and the check stays silent when offline. (CAP-1; AD-20)
- E13-R8: Each tagged release builds every app in CI and attaches it to the GitHub Release. The release also carries `SHA256SUMS`, the updater artifacts with their signatures, and `latest.json` for each channel. It sits beside the npm publish, which is unchanged. Builds are unsigned at first. Apple notarization and Windows signing are pipeline slots that turn on when the user's secrets exist and do nothing without them. (CAP-1, CAP-20; AD-13 note on pins)
- E13-R9: The first run inside the app is the same Welcome, worded for an app: it never says "terminal" or "npx", and it does not offer the app shortcut, because the app is the shortcut. Each download has plain "how to open an unsigned app" steps for macOS (Privacy & Security, Open Anyway), Windows (SmartScreen, More info, Run anyway) and Linux (making the AppImage executable). The webview requirements are stated: WebView2 on Windows, and webkit2gtk-4.1 on Linux. (CAP-16, CAP-1; AD-21)
- E13-R10: The app works on macOS, Windows and Linux on each architecture listed in E13-R1. Its end-to-end checks pass in CI, the user's live checks pass on all three OSes, and the first app release ships beside the npm release of the same version. (CAP-1, CAP-20)

### What the research found (2026-10-04)

"V" means seen on official docs, release pages or the GitHub API. "R" means reported, or not confirmed on an official page.

- Tauri: `tauri` and `@tauri-apps/cli` 2.12.1 (2026-09-30) are the stable release (V). Tauri 3.0.0-alpha.4 exists and is not targeted. The plugins are updater 2.12.0, shell 2.3.6 and single-instance 2.4.5 (V). `tauri-apps/tauri-action@v1` (2026-06-29) supports Tauri v2 only and writes `latest.json` with `uploadUpdaterJson`; its download URLs point at github.com (V). The Rust MSRV is 1.90 on `dev` (V; check the tag).
- Sidecar: `bundle.externalBin` with a `-<target triple>` suffix; spawned from Rust with `app.shell().sidecar(..)`. Tauri does not supervise it: the shell must kill it on `RunEvent::ExitRequested`. On Windows, killing the direct child leaves its children (R).
- Node: 24.21.0 is Active LTS, 22.23.3 is in maintenance, and 26.10.0 is Current with LTS expected late October 2026 (V). SEA is "1.1 Active development"; `--build-sea` is from 25.5; ESM works with `useVfs`; native addons must be extracted and `dlopen`ed (V). A Node download is 27 to 53 MB compressed (V), and about 100 MB unpacked (R).
- Webview: WebView2 is preinstalled on Windows 10 1803 and later and on Windows 11 (V). The `webviewInstallMode` options add about 0 MB (`downloadBootstrapper`), 1.8 MB (`embedBootstrapper`), 127 MB (`offlineInstaller`) or 180 MB (`fixedRuntime`) (V). Linux needs webkit2gtk-4.1, built on 22.04 or Debian 12 (V). macOS `minimumSystemVersion` defaults to 10.13 (V).
- Platforms: macOS builds per architecture or `universal-apple-darwin` (V). Windows ARM64 needs the ARM64 C++ build tools, and NSIS bundles ARM64 binaries (V); MSI on ARM64 is unknown (R). Linux ARM AppImages build only on ARM runners; a `.deb` cross-compiles (V). MSI needs WiX on Windows (V).
- Updater: `tauri signer generate` makes a minisign key pair. `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` must be environment variables, because `.env` files are not read. `bundle.createUpdaterArtifacts: true` makes `.app.tar.gz`, `.AppImage`, and the NSIS and MSI artifacts, each with a `.sig`. `latest.json` holds `version`, `notes`, `pub_date` and `platforms` keyed `<os>-<arch>` with `signature` and `url`. Endpoints take `{{target}}`, `{{arch}}` and `{{current_version}}`, and several endpoints are allowed. Downgrades are refused by default. Windows `installMode` is `passive`, `basicUi` or `quiet`, and the app exits to install; elsewhere the app relaunches (V). Only the AppImage self-updates on Linux, not the `.deb` (R). The updater works without Apple notarization because it checks its own signature (R).
- Single instance: the plugin registers first, and its callback gets `(app, args, cwd)`. On Linux it uses DBus (V).
- Unsigned apps: Apple has removed Control-click > Open. Users go to System Settings > Privacy & Security > Open Anyway, which needs their password and is offered for about an hour (V). `xattr -dr com.apple.quarantine` also works (R). Ad-hoc signing (`signingIdentity: "-"`) is needed to run on Apple silicon (V). Windows shows SmartScreen > More info > Run anyway (R). Notarization takes `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `KEYCHAIN_PASSWORD`, plus `APPLE_API_ISSUER`, `APPLE_API_KEY` and `APPLE_API_KEY_PATH`, or `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID`. Windows signing takes a .pfx thumbprint, Azure Artifact Signing (formerly Trusted Signing) or a `signCommand`. EV certificates no longer skip SmartScreen (V).
- Security: capabilities are scoped by window, and remote content has no IPC unless a capability's `remote.urls` grants it (V). The localhost plugin serves Tauri's own assets over HTTP and carries "considerable security risks", so it is not used (V).
- Code facts: the data folder is `envPaths('ogden-agents',{suffix:''}).data`, overridden by `OGDEN_AGENTS_DATA_DIR`. The instance lock (`instance-lock.ts`) makes a losing server exit with code 3. `killProcessTree` uses `taskkill /T /F` on Windows and SIGKILL on the process group elsewhere. `serve.ts` closes on SIGINT and SIGTERM. Migrations run on open. `DEFAULT_PORT` is 4317. Native modules are better-sqlite3 13, @napi-rs/keyring 2.1 and the optional node-pty 1.1. Nothing checks npm for a newer version today.

### Updater key: the user's steps (13.9, hitl; never done by an agent)

The user runs these on their own machine. No agent generates, sees or stores the key.

```sh
# 1. Generate the key pair (asks for a password; keep it).
npx --yes @tauri-apps/cli@2.12.1 signer generate -w ~/.tauri/ogden-agents-updater.key
# 2. Store the private key and its password as secrets of the desktop-release environment.
gh secret set TAURI_SIGNING_PRIVATE_KEY --env desktop-release --repo hsmith-dev/ogden-agents < ~/.tauri/ogden-agents-updater.key
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --env desktop-release --repo hsmith-dev/ogden-agents
# 3. Give the public key (~/.tauri/ogden-agents-updater.key.pub) to 13.9's builder, which commits it to tauri.conf.json `plugins.updater.pubkey`.
# 4. Back the private key and password up offline. If they are lost, installed apps can never update again and every user must reinstall by hand.
```

The `desktop-release` environment is created first, as `npm-release` was (Settings > Environments, a tag rule `v*.*.*`, the user as required reviewer).

- Spec (applied): a new CAP-20, "Ogden as a desktop app". Intent: a user downloads and opens Ogden Agents as an app on macOS, Windows or Linux, with nothing else to install, and it keeps itself up to date. Success: on a fresh machine with no Node, the downloaded app reaches a first chat with no terminal, and updates from N to N+1 without losing data or interrupting running work. CAP-1's Assumption ("the one install command is the only CLI step") gains: the desktop app needs no command at all. Constraints: "a single Node process" stays true inside the app.
- Initiative: a dated note and the epic 13 line under its own heading, "desktop app (planned; outside the v1 initiative's Done when)".
- AD-3 note: in the app, the shell owns the server's life. Quitting the app quits a server it started (Quit's busy rule), never an npm-started one it attached to. The server also exits when its parent shell is gone. The npm route is unchanged.
- AD-15 note: "AD-15 in a webview". The shell opens `/#c=<code>` from `/launcher/hello?launch=1` with the launcher token. The webview's origin is the server's own, with no Tauri IPC or capability on it, and navigation is locked to that origin. The known limit (the launch URL on a process command line) does not apply to the app, which passes no URL on a command line.
- AD-5 note: on a version change the database is copied to `<dataDir>/backups/` before migrations, and a database newer than the running server is refused with a plain message.
- AD-20 note: an app update is offered through the server. The shell reports an available update with a launcher call, the UI shows "Update available — Restart to update", and the restart waits for no busy session or running build. npm installs get a notice from a registry check that can be turned off. Downgrades are refused, and a newer database is refused.
- AD-21 note: distribution has two routes, `npx ogden-agents` and the desktop app. The app bundles a pinned Node runtime and needs no install step.
- New AD-23, distribution and update signing: desktop apps are built only by the release workflow from a tag, with pinned Node binaries checked by SHA-256 per OS and architecture, and published as GitHub Release assets with `SHA256SUMS`. Updates are signed with the user's own minisign key, kept only as a GitHub Actions environment secret. Code signing and notarization are optional pipeline slots fed by the user's secrets.
- Stack: Tauri 2.12 (Rust), tauri-plugin-updater, -single-instance, -shell, -process and -opener; tauri-action v1; a new `packages/desktop/` (the `src-tauri` crate and its build scripts).
- EXPERIENCE.md and DESIGN.md (not applied here; 13.3 writes them): the app's launch (no "terminal" wording), the update prompt (app and npm), the app menu, quit with busy sessions, and the "how to open" pages.

### Open questions (2026-10-04; all answered by the user the same day, see Approval; kept as asked)

1. Release line: does the desktop app wait for v1 (epic 6's release), or ship as soon as it passes, beside the current npm version? Recommendation: ship when ready. The app wraps whatever server version is current, and waiting adds nothing.
2. Update check frequency and download: on start and every 6 hours, downloading in the background once found, then prompting? Or prompt before downloading? Recommendation: check on start and every 6 hours, download in the background (verified, not installed), then prompt "Restart to update".
3. A running build when an update is ready: wait until it finishes, or let the user restart anyway with a warning that the build will be interrupted and resumed or failed? Recommendation: "Restart to update" is disabled while a chat turn is running. With a running build it warns and offers "Restart when builds finish", which waits for the builds to finish and restarts automatically; it never kills a build.
4. Quitting the app when the server was started by `npx ogden-agents` (the app attached to it): stop it too, or leave it running? Recommendation: stop it, the same as Quit in the UI, with the busy confirmation.
5. Channels: the next channel's `latest.json` needs a fixed URL, but GitHub's `releases/latest` skips prereleases. Use a permanent prerelease named `desktop-channel-next` whose `latest.json` asset each rc replaces (stable uses `releases/latest/download/latest.json`)? Recommendation: yes; it needs no server and no Pages site.
6. Tray icon: none in the first version (quit means stop, AD-3), or a tray icon that keeps the server running with the window closed? Recommendation: none in v1. Closing the window on macOS keeps the app in the Dock, as Mac apps do. On Windows and Linux closing the window quits, with the busy confirmation.
7. macOS: two `.dmg` files (Apple silicon, Intel) or one universal `.dmg` (about twice the size, one download)? Recommendation: two, with the download page picking for the user.
8. The npm notice sends a request to the npm registry, which Ogden does not make today ("no telemetry"). Should it be on by default with a Settings switch, or asked once? Recommendation: on by default, disclosed in Settings with a switch. It sends nothing but the package name.
9. Who applies the proposed deltas, and when? Recommendation: through `bmad-spec` and `bmad-architecture` on approval, as a hard gate before 13.2 starts (13.2 already quits the server with its window, which the AD-3 note allows). Then CAP-20 joins `covers` and the initiative's covers.
10. 13.9's check: `release.yml`'s guard refuses any tag not on `main`'s first-parent history and not matching the package versions. Check the desktop part with a `workflow_dispatch` dry run on `main` (no tag, no npm publish, a draft release deleted afterwards, using the user's key behind the `desktop-release` reviewer)? Recommendation: yes. The alternative is to check it only at 13.13's first prerelease.
11. Placement: does the desktop app belong in this initiative with a new CAP-20, outside the v1 Done when as drafted, or in its own follow-on initiative? Recommendation: this initiative, with CAP-20, under its own heading, as v1.1 is.
12. Test signing: CI test builds use a throwaway updater key and replace the public key in that build only. Releases always use the user's key. Is that acceptable? Recommendation: yes. It is the only way CI can test N to N+1 without anyone else holding the user's key.
