# Pick Codex or Gemini CLI beside Claude Code for any chat, project or build

## Description

Today Ogden Agents has one agent. The server wires a single `AgentPort` (`createClaudeCodeAgent` in `packages/server/src/start.ts`), a session has no agent field, and the web names the agent through constants (`AGENT_ID`, `AGENT_NAME` in `packages/web/src/chat/chat-api.ts`). This epic makes the agent a choice. Each chat picks its agent when it starts, and each project has a default agent that is preselected. Codex (through the official `@agentclientprotocol/codex-acp` adapter) and Gemini CLI (through its native `gemini --acp`) join Claude Code, and further ACP agents become one adapter each. The herdr-style status sidebar stays on throughout. Every project, Simple or BMad, can hold many chats with different agents at once, and each row names its agent. Each agent is installed and signed into from the UI with no terminal, using a subscription or an API key kept in the keychain. Each agent gets the terminal toggle where its CLI can resume the ACP session. Where a project turned Planning on, the agent gets the BMad skills, and with Unattended builds on, the agent can build through epic 5's runner and sandbox chain. The shared ACP client code is extracted from `acp-claude-code` first, so each new agent adds an adapter and a wiring line and does not change core (AD-1).

## Outcome

A user picks Claude Code, Codex or Gemini CLI for each chat, and for each build where builds are on, in any project, with several agents working at once. CAP-15's success criterion is the signal: each supported agent completes a `bmad-build-auto` run through the UI, and each agent that speaks ACP also completes a chat. So is CAP-3's two-agent resume proof, which epic 2 moved here. The demo: in one Simple project, a Codex chat and a Claude Code chat both run at the same time, both survive a server restart, and the Codex one switches to its terminal and back.

- E6-R1: A session carries the agent it was started with (`agentId`, set at creation and never changed). A project has a default agent, kept by core on the workspace row and changed only through the workspace settings use-case. New chats preselect that default, and the composer's agent picker applies to new sessions only (EXPERIENCE.md Composer). Sessions stored before this epic read as `claude-code`. Any number of sessions with any mix of agents run at once, across any number of projects. The sidebar, the session header and Needs you name each session's agent by its product name. (CAP-15, CAP-3, CAP-17; AD-2, AD-3, AD-8, AD-9; EXPERIENCE.md Composer, Empty chats, Workspace settings)
- E6-R2: The agent is chosen by data, not by branches. Server wiring builds a registry of the installed agents' `AgentPort` and `AgentSetupPort` by `AgentId`, and core looks up the session's agent through it. Core names no agent, and an architecture test fails if `packages/core` or `packages/shared` names an agent id outside tests. Adding an agent means adding its adapters and one wiring entry. An agent that is not installed, or not signed in, refuses a new chat with a plain reason and an action. (CAP-15; AD-1, AD-9, AD-11)
- E6-R3: All ACP agents share one ACP client implementation, extracted from `acp-claude-code` with no change in behaviour. It covers ACP wiring, the `session/update` mapping, the AD-4 state mapping, the reopen order (`session/resume`, then `session/load`, then a new session primed from the stored transcript), permission requests, `auth_required`, secret masking, timeouts and stopping the process tree. Each agent's adapter supplies only what is its own: how to spawn it, its auth methods, the tool input fields that name paths, its terminal resume, and its transcript reader. (CAP-15, CAP-3, CAP-4; AD-1, AD-4, AD-5)
- E6-R4: Codex and Gemini CLI chat through ACP. Each has permission cards, where Allow once picks the agent's option of kind `allow_once` and Deny picks `reject_once`. Ogden never picks `allow_always` or an agent's own session-wide option (Codex's `allow_for_session`, Gemini's ProceedAlways), because always-allow stays core's (agent-matrix "Permission cards"). Each also has the normalized states and resume: Codex through `session/resume`, Gemini CLI through `session/load`. The two-agent resume proof of CAP-3 is shown with Claude Code and Codex. (CAP-15, CAP-3, CAP-4; AD-4, AD-5)
- E6-R5: Each agent is found, installed, signed into and given an API key from the UI, through one `AgentSetupPort` adapter per agent. Install goes into the data folder from a pinned `package.json` and lockfile, checked in CI as Claude Code's are. Sign-in uses the agent's own methods: Codex's ChatGPT browser or device-code login, and Gemini CLI's Google login, through ACP `authenticate` or the CLI's own login in a hidden PTY, whichever the spike finds works headless on all three OSes. API keys are kept under `agent-api-key/<agentId>` in the keychain and passed only in that agent's child environment, under the agent's own variable name (`CODEX_API_KEY`, `GEMINI_API_KEY`). Logs redact each provider's key format. The agent card names the provider from the agent's setup status (the deferred 9.2 item). (CAP-16; AD-15, AD-16, AD-21; EXPERIENCE.md Settings: Agents, Welcome)
- E6-R6: The terminal toggle is offered for an agent only where its CLI resumes the ACP session id. Codex (`codex resume <id>`) is expected to qualify. Gemini CLI qualifies only if the spike confirms that `gemini --resume <uuid>` resumes the ACP session. Any other agent gets `agent_unsupported` with its name. `agent-matrix.md` records the result for each agent. (CAP-5; AD-6, AD-19; agent-matrix "Terminal toggle")
- E6-R7: In a project with every BMad piece off, every agent works with nothing BMad added to its sessions and nothing written into the repo. In a project with Planning on, BMad's skills reach the session's agent: setup places them in each in-use agent's skill folder (`.agents/skills` for Codex and Gemini CLI, `.claude/skills` for Claude Code), and the agent's adapter formats the skill invocation. Core still names no skill. Gemini CLI reads `AGENTS.md`, so retrospective pitfalls reach it. (CAP-15, CAP-19, CAP-6, CAP-13; AD-12, AD-22; bmad-integration.md)
- E6-R8: In a project with Unattended builds on, the Build dialog lets the user choose the agent for each build, defaulting to the project's agent. The run records it, and epic 5's runner runs that agent's bmad-loop profile. The sandbox chain runs per agent and per OS: the agent's native sandbox, then Docker, then the three choices. The Build dialog's "use another agent" choice lists only agents that can build unattended on this computer. Build all ready (epic 11) uses the project's default agent, and the run header shows the run's agent. Any first-run prompt in an agent's profile (Codex's workspace trust and hook trust, Gemini's workspace trust) is answered by the server, never by the user in a terminal. (CAP-15, CAP-8; AD-17, AD-21; agent-matrix "Unattended builds")
- E6-R9: Every agent works on macOS, Windows and Linux. OS-sensitive behaviour is probed in CI on all three, Windows first, before it is built. That covers spawning each agent and resolving its binary, the auth flows, resume, and each agent's native sandbox. Each agent's adapter and CLI version is pinned with a lockfile, and a bump is a reviewed change. Each supported agent passes a live check recorded in its plan. (CAP-15, CAP-1; AD-13, AD-19, AD-21)

## Done when

1. In one project with every BMad piece off, a Claude Code chat, a Codex chat and a Gemini CLI chat run at the same time. Each shows permission cards that hold a shell command until it is approved, and normalized states, with the agent picked per chat and the project's default preselected. After a server restart, the Claude Code and Codex chats continue with their context (CAP-15, CAP-3, CAP-4, CAP-19; E6-R1 to E6-R4).
2. On a fresh machine, a user installs Codex and Gemini CLI from the UI and signs into each with a subscription. Another user chats with each using only an API key, and no key appears in the database, the event log or the logs (CAP-16, AD-16, AD-21; E6-R5).
3. The terminal toggle appears for exactly the agents and OSes `agent-matrix.md` lists. The matrix has no "verify" cells left for the v1 agents (CAP-5; E6-R6).
4. With Planning on, a planning session with Codex runs a BMad skill. With every piece off, no agent's session gets a BMad skill or text (CAP-6, CAP-19, AD-22; E6-R7).
5. Each supported agent completes a `bmad-build-auto` run through the UI in a project with Unattended builds on, sandboxed or attended as the matrix says for that OS (CAP-15, AD-17; E6-R8).
6. The epic's end-to-end suite passes on macOS, Windows and Linux. It is released in an `ogden-agents` npm version after epic 5's, and each supported agent's live check is recorded (E6-R9).

## Boundaries

This epic covers Codex and Gemini CLI as full agents (chat, sign-in, terminal toggle where the CLI allows it, and builds), and the mechanism that makes any further ACP agent one adapter. GitHub Copilot CLI and Antigravity are not in this draft's scope until the user decides (open question). bmad-loop already has profiles for both, and both now have ACP entries, but Copilot's ACP is in public preview and Antigravity's is a proprietary binary. Other ACP-registry agents (OpenCode, Cursor, Goose, Qwen Code and others) are deferred. Core, `BuildRunnerPort`, `SandboxPort` and the dispatcher (5.8) do not change. The only exceptions are the shared and core field changes that E6-R1 and E6-R2 need (proposed AD notes below). No model or mode picker. No cost or token tracking (AD-8). No change to the caution levels or to how always-allow rules match, beyond adding each agent's own config folders to the protected names. Epic 5 owns the build runner, the sandbox chain and the Build dialog, which this epic only extends with agent profiles. Epic 4 owns BMad setup, which this epic only extends with agent skill folders. Retrospectives are epic 7.
