# A linked Jira board drives BMad's ticket tree and board as "Tooling Drive", local files still the only route to a build

## Description

A user links an existing Jira board to an Ogden Agents project. Its epics and stories appear in BMad's ticket tree and on the Board without hand-authoring `tickets.toml`; a ticket built and approved in Ogden pushes its status out to the matching Jira issue; a status change made directly in Jira comes back on the next sync. Jira is the source of truth for what a human sees and edits there day to day — status, assignment, which issues exist — but the local BMAD files stay what `bmad-build-auto` and `tickets.py` actually route and build off of (AD-10): sync updates those files, it never bypasses them. This is presented to the user as **Tooling Drive**, a first-class project mode alongside **Simple** and **BMad Method** (CAP-19's three-way picker, not yet built anywhere in this repo — the only existing "project mode" work is the unrelated approve-each/automatic orchestration-dispatch toggle, and the only existing BMad on/off UI is AD-22's per-piece checkboxes), not a buried sub-setting.

The three architecture decisions that resolve CAP-26 are adopted: AD-27 (pull-only polling, never a webhook), AD-28 (field mapping — only a clean native Jira match syncs; the local file keeps the deciding vote on every conflict), and AD-29 (API token auth through the existing keychain pattern, not OAuth). Both of AD-29's open sub-points are closed by this epic, not carried into implementation (see Notes: Decision lines).

## Outcome

A user who already runs their team's work through Jira links its board once and gets BMad's planning, board and unattended-build machinery for free, without re-entering their backlog or losing Jira as the place their team and stakeholders actually look; CAP-26's own success signal — ticket tree and Board populated with no hand-authored file, a build's `done` reaching Jira, a Jira-side status change reaching the local tree on the next sync — is the measure.

## Requirements

- E18-R1 (CAP-26): A user links a Jira board to a project by entering the site URL, their Jira account email, and an API token (or Data Center Personal Access Token); Ogden makes one read-only test call (`GET /rest/api/3/myself` or the Data Center equivalent) and shows it as a permission-card-style confirmation before saving anything.
- E18-R2 (CAP-19, amended; CAP-26): The project-mode choice becomes three equally-weighted options — **Simple**, **BMad Method**, **Tooling Drive** — at project creation and in workspace settings, replacing the single on/off framing. Choosing Tooling Drive sets up BMad Method (Planning and Board) and links the Jira board in the same one step; linking a board when Planning or Board is off bootstraps them the same way (AD-22 note, 2026-10-07).
- E18-R3 (CAP-26): A linked board's epics and stories appear in BMad's ticket tree and on the Board without a hand-authored `tickets.toml`; a Jira issue not yet in the tree gets its local file on first sync, matching the tracker-store convention already designed for this case.
- E18-R4 (CAP-26, AD-10, AD-17): A ticket Ogden builds and the user approves pushes `done` to the matching Jira issue's Status immediately, as part of approving — never deferred to the next poll, never written by a sync in either direction otherwise.
- E18-R5 (CAP-26): A status change made directly in Jira is reflected back in the local ticket tree on the next sync (the interval poll or an explicit Refresh), always through the same `tickets.py mark` path any other status change uses (AD-10).
- E18-R6 (CAP-26's own constraint and non-goal): At no point does a linked board drive `bmad-build-auto`'s dispatch or a ticket's build routing directly — only the local BMAD files do; Jira sync updates those files, it is a synced remote, never a second routing authority. `after`/prerequisites flow local → Jira only and are never read back, so Jira's link graph never drives build order even though a human reading Jira sees the same dependency.
- E18-R7 (AD-27): Sync is polling-only — a fixed interval (default 5 minutes) that runs only while at least one tab is subscribed to that workspace's event stream, stopping when the last such subscription ends — plus the Board's Refresh action, debounced to once every 10 seconds per workspace. Ogden never registers or receives a Jira webhook; no inbound route is added. A failed sync shows a dismissible "last synced at `<time>` — retry" notice and never blocks the Board from showing its last-synced local state.
- E18-R8 (AD-28): Only BMad frontmatter fields with a clean native Jira counterpart sync, per AD-28's table (title/Summary, body/Description, status/Status, type/Issue Type, parent/Epic-link, assignee/Assignee, severity/Priority, after/prerequisites one-way); everything else (`risk`, `estimate`, `estimate_basis`, `hitl`, `covers`, `references`, `unknown`, `blocked_at`, `blocked_reason`) stays local-only and is never pushed. Ogden creates no Jira custom field in v1.2.
- E18-R9 (AD-28): The sync baseline (each two-way field's value at the last successful sync) is kept beside the ticket's own plan file, never in the database (AD-10). A field changed on both sides since the last sync is a genuine conflict: Ogden never guesses a merge, keeps the local value, shows a "Jira also changed this" notice, and only an explicit Refresh — never the background poll — may overwrite local with Jira's version. A pulled Jira status with no valid local transition, or a Jira "done"-equivalent pull with no matching local approve, surfaces the same notice rather than being coerced or silently dropped.
- E18-R10 (AD-29): Authentication is an API token (Jira Cloud) or Personal Access Token (Data Center), never OAuth, for v1.2. The token alone is the secret, stored bare through the existing `SecretStorePort`/OS-keychain mechanism (AD-16) under `jira-credential/<workspaceId>`, matching `agent-api-key/<agentId>`'s one-key-one-secret shape. The Jira account email and site URL are ordinary, non-secret workspace settings kept outside the keychain. A classic token's base URL (`<site>.atlassian.net`) and a scoped token's (`api.atlassian.com/ex/jira/<cloudId>`) are both resolved inside the `tickets-jira` adapter at link time.
- E18-R11 (AD-27, AD-29, security review finding 2): The Jira site URL is confirmed once at link, bound to that host (a changed host asks again), and restricted to `https://`; redirects are refused; the resolved host is checked and rejected if it is loopback, link-local, or in a private address range, before the poller is ever allowed to start sending the stored token to it, and again on every host change.
- E18-R12 (AD-16, AD-29, security review finding 1): `tickets-jira`'s redaction treats the whole stored value — token, email, and site URL together — as in scope for redaction before anything is logged or emitted, not a token-shaped substring match; this matches the existing webhook-URL precedent (AD-16) rather than the per-provider-token-format precedent.
- E18-R13 (AD-29, closing its own open sub-points — see Notes: Decision): OAuth is out of scope for v1.2; the credential is scoped per linked board (`jira-credential/<workspaceId>`), not per Jira site.

## Done when

1. A user in a project with Tooling Drive chosen links a Jira board; its epics and stories appear in the ticket tree and on the Board within one sync, with no hand-authored `tickets.toml` entry for any of them.
2. Approving a ticket in Ogden updates the matching Jira issue's Status at once; a status edited directly in Jira appears in the local ticket tree after the next poll tick or a Refresh click, and every one of those local writes goes through `tickets.py mark` (AD-10) — never a store bypass.
3. Stopping, disabling, or never linking Tooling Drive changes nothing about how `bmad-build-auto` dispatches or routes a build: it reads only local files either way (E18-R6), proven by a test that asserts the dispatcher's query path never imports or calls anything Jira-specific.
4. Pasting a site URL that is plain `http://`, that redirects to a different host, or that resolves to a loopback, link-local, or private-range address is refused at link time with a plain reason, before any credential is saved or any poll interval is scheduled.
5. A sync failure, a redaction test, or a deliberately triggered log/event path that would otherwise carry the stored token, email, or site URL shows full redaction of all three, not a substring match on the token alone.
6. Unlinking a board deletes `jira-credential/<workspaceId>` from the keychain immediately (a direct keychain read afterward finds nothing), and the tickets already synced in stay as ordinary local files, buildable exactly as any other local ticket.

## Boundaries

Jira only — no other tracker (Linear, GitHub Issues, Notion, Trello stay out of scope per the spec's own non-goal). No OAuth (E18-R13). No inbound Jira webhook or new unauthenticated route of any kind (AD-15 unchanged). No change to `bmad-build-auto`'s dispatch or routing logic itself, beyond the `tickets-jira` adapter and the pieces/mode plumbing that choose it — CAP-26's non-goal that a tracker never drives build routing is a hard boundary, not a trade-off this epic revisits. The three-way project-mode picker (E18-R2) is scoped to presenting and wiring the choice, including Tooling Drive's one-step bootstrap of BMad Method; it does not redesign Simple or BMad Method mode's own existing behavior.

## Notes

- Decision (2026-10-07, this epic's inception, closing AD-29's first open sub-point): OAuth is out of scope for v1.2, including as a later opt-in flag. AD-29's own text already makes the case (no secretless OAuth 2.0 path exists for a public client against Jira Cloud today, and Ogden ships as an npm package with no server to hold a confidential client's secret); nothing surfaced in this epic's slicing changes that calculus, so there is no "later opt-in" scaffold to build now. Revisit only if Atlassian ships a secretless OAuth path for Jira Cloud, per AD-29's own text.
- Decision (2026-10-07, this epic's inception, closing AD-29's second open sub-point): the credential is scoped **per linked board** (`jira-credential/<workspaceId>`), not per Jira site. AD-29's own keying already implies this; the alternative — one credential per Jira site, reused across several boards on that site — is explicitly declined, because (a) it would need a second keyed-by-site lookup layer and a way to detect "same site" across workspaces that AD-29 never specifies, (b) a project's board and the project's workspace are already a one-to-one relationship everywhere else in this spine (AD-9, AD-11), so per-board keeps that invariant, and (c) per-site reuse would mean revoking or rotating one board's token silently affects every other board on the same site sharing it, which is a surprising blast radius nothing in AD-16's existing credential-lifecycle pattern anticipates.
- Decision (2026-10-07): the three-way project-mode picker (E18-R2) is built as a new control that supersedes the existing BMad on/off entry point in workspace settings and Welcome's project step, while leaving AD-22's per-piece contract (`BmadPiece`, `requireBmadFeature`, `bmad-piece-choice.tsx`'s availability/dependency logic) untouched underneath: Simple maps to all pieces off, BMad Method maps to the user's existing per-piece choices (unchanged), Tooling Drive maps to Planning + Board on (at minimum) plus a linked Jira board. The granular per-piece checkboxes stay reachable as an "Advanced" or secondary control under BMad Method, since AD-22's dependency and coming-soon rules are per-piece and still need a surface; the three-way picker is the primary, first-class choice CAP-19 asks for, not a replacement for every granular control.
- Assumption: "Tooling Drive" requires Planning and Board at minimum (to populate the ticket tree and Board) but not Builds or Retrospectives, which the user may still choose independently per AD-22's existing dependency rule; unconfirmed by the user, flagged for review during inception of the stories that implement E18-R2.
- Decision (2026-10-07, this epic's inception, resolving the unlink open question raised while drafting Requirements): unlinking a Jira board drops the project back to plain BMad Method mode — Planning and Board stay on, the already-synced tickets stay as ordinary local files — rather than asking the user what to do next (entry 9). AD-28's local-file convention already answers what happens to the tickets, so no further choice was needed.
- Decision (2026-10-07, this epic's inception, sequencing): the tracer bullet (entry 1) carries a live hitl check against the developer's own Jira Cloud sandbox, not a fixture-only slice, because AD-29's classic-vs-scoped-token base-URL resolution and the real `/myself` call are exactly the kind of "does this actually work against Jira" risk a tracer exists to retire early; every other entry builds and verifies against the fake Jira server fixture from entry 2, with the live sandbox reused only for entry 12's closing suite.
- Decision (2026-10-07, this epic's inception, sequencing): entries 1-7 (contracts through polling) are one lane in `packages/core` and `packages/adapters/src/tickets-jira`, built strictly in order since each reads the previous entry's stored shape (baseline, credential, resolved URL); entries 8-10 (conflict UI, unlink, the three-way picker) are a second lane in `packages/web`. Entry 8 opens once entry 6 lands and may proceed beside entry 7, 9 and 10, since it touches no component any of them do. Entries 9 and 10 are sequential with each other, not parallel: entry 10's picker surfaces entry 9's Unlink action when moving a Tooling Drive project to BMad Method or Simple, so entry 10 needs entry 9 built first (`after = [4, 9]` in the breakdown).
- Flagged for review, not guessed past (2026-10-07, this epic's inception): AD-22's note says linking a board bootstraps Planning/Board "when Planning or Board is off," worded as if a board could be linked from somewhere other than choosing Tooling Drive in the picker (entry 10). This epic does not add a second "link a board" entry point outside the picker; to keep AD-22's note true regardless, entry 4's link use-case itself does the bootstrap (not entry 10's UI), so the behavior holds even if a second entry point is added later. Whether a second entry point should exist in v1.2 at all is a product-surface question, not an engineering one, and is left to the user to confirm before or during entry 10's build; entry 4 is unaffected either way.
- Waits on epic 10 because: this epic's three-way picker is built directly on AD-22's `BmadPiece` contract and existing settings UI; it does not re-derive piece gating.
- Waits on epic 4 because: `tickets-jira` is a second adapter behind the same `TicketStorePort` `tickets-v7` already implements, and the Board/ticket-detail UI this epic's synced tickets appear in already exists there.
- Waits on epic 9 because: `SecretStorePort`/keychain storage (AD-16, story 9.2) and Welcome's project-creation step (9.5), where Tooling Drive is offered as a creation-time choice, both ship there.
