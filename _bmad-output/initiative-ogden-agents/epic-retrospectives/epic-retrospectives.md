# Each finished epic teaches the next one

## Description

In a project where the user turned on Retrospectives (epic 10, AD-22; it needs Board, user decision 2026-10-02), an epic on the board offers **Look back on this epic**, and a finished one also offers it once, never starting it by itself. It starts an ordinary agent conversation of kind `planning` in the session view (epic 4's planning session) in which BMad's own retrospective skill reads the epic's evidence (its epic file, tickets, plans, diffs and commits, plus Ogden's short build summaries of the epic's runs, never full transcripts) and writes `epic-<slug>-retrospective.md` beside it, with sourced findings, action items, proposed `AGENTS.md` pitfalls and a verdict. The transcript's document card then offers the two ways the lessons flow back, each an agent conversation the user approves: **Add the lessons to AGENTS.md** (BMad's project-context skill) and **Turn the action items into tickets** (BMad's ticket skill). **Save the lessons for later builds**, and only that click, commits `AGENTS.md` and the retrospective file, so every later build's worktree, which branches from the checkout's last commit, carries the new pitfall. The board shows each epic's verdict. Ogden builds no retrospective logic of its own: it starts the sessions, reads the verdict, and makes one commit on request.

## Outcome

CAP-13's success criterion is the signal: after an epic completes, a retrospective file exists beside it and a later build includes the new pitfall. The second signal is that a project with Retrospectives off, including every Simple project, never shows or runs any of it.

## Requirements

Each line maps to CAP-13 and names the architecture decisions and UX sections it carries. - E7-R1: Retrospectives exist only in a project with the `retrospectives` piece on, which needs what 10.2's dependency rule says, and the project's script trust (4.2). This epic adds `retrospectives` to `SHIPPED_BMAD_PIECES`; every core use-case it adds (start a look-back, read verdicts, dismiss the offer, save the lessons) calls `requireBmadFeature(workspaceId, 'retrospectives')`, every route goes through `bmadPieceRoutes`, and nothing runs, is read or is written for a workspace with it off. A Simple project, and a project with Board on but Retrospectives off, shows no look-back action, offer or verdict. Ogden never starts a retrospective on its own. (CAP-13, CAP-19; AD-22, AD-1, AD-11)
- E7-R2: **Look back on this epic** on the board's epic header starts a session of kind `planning` through a core use-case guarded by `retrospectives` (not `planning`), whose first message invokes the catalog's epic-scoped look-back action with the epic's folder, formatted by the agent adapter so core and web name no skill (AD-12). The session is interactive in the session view with permission cards, so the user answers the skill's going-in question and any confirmations in the chat; no headless run. The first message also carries a short build summary per run of the epic's tickets from Ogden's run records (outcome, verification result, blocked reason, duration), never a full transcript; with no runs (an epic built by hand) none is given and the skill records the gap (user decision 2026-10-02). An epic with tickets not yet finished still offers it, with one line saying the look-back will record the epic as not accepted (user decision 2026-10-02). (CAP-13; AD-8, AD-12, AD-18; EXPERIENCE.md Component Patterns "Planning session", "Board")
- E7-R3: When every ticket in an epic is finished (`done` or `dropped`), its epic header on the board shows one offer, "Every ticket in this epic is done. Look back on it?", with **Look back** and **Not now**, remembered per epic by core; it is derived from the ticket index, needs no new event, and never starts a session by itself. (CAP-13; AD-7, AD-10, AD-22)
- E7-R4: The retrospective lives in the repo, where the skill writes it: `epic-<slug>-retrospective.md` in the epic folder, written by the agent behind permission cards; Ogden writes none of it. Epic 4's document card shows it with **Open**. The board's epic header shows the verdict (Accepted, Accepted with open items, Not accepted) and date, read only from the file's frontmatter `verdict` and `date` by the `tickets-v7` adapter (never the prose), refreshed when the watcher sees the file change (4.8 emits `ticket.changed` only for changed ticket rows, so entry 2 freezes a refresh for a changed retrospective file); a missing or unreadable verdict shows as no verdict plus a one-line notice, never a guess. (CAP-13; AD-7, AD-10, AD-14; bmad-integration.md Files Ogden Agents reads "Retrospective")
- E7-R5: Pitfalls reach later builds. The retrospective's document card offers **Add the lessons to AGENTS.md**, a planning session invoking the catalog's project-context action on the retrospective file, in which the agent edits the project's `AGENTS.md` behind permission cards. Then **Save the lessons for later builds** commits exactly `AGENTS.md` and that retrospective file to the branch the main checkout has checked out, locally, through a core use-case and `VcsPort` (never a push, never another path, refused with a plain reason when neither has a change or a merge or rebase is in progress). A build dispatched after it carries the pitfall in its worktree's `AGENTS.md`, which the build runner loads (5.7), and neither approve's clean-checkout check nor dispatch's (5.5) is blocked by an uncommitted `AGENTS.md`. (CAP-13; AD-17, AD-10, AD-11; bmad-integration.md "Pitfalls", Writes)
- E7-R6: Action items flow back as tickets the user approves. The document card also offers **Turn the action items into tickets**, a planning session invoking the catalog's ticket action on the retrospective file, in which the agent proposes entry and note changes and makes those the user approves through BMad's own ticket tooling; Ogden writes no ticket, and new or changed entries reach the board through the watcher. (CAP-13, CAP-7; AD-10, AD-12)
- E7-R7: The look-back, the lessons and the action-item actions come from Ogden's own label mapping in the bmad-catalog adapter (no fork; story 4.14), not from code in core or web: `bmad-retrospective` gets an epic scope (it takes an epic folder and appears on the board's epic header, not in Plan home) and two further next steps, and `bmad-project-context` a plain label for recording lessons. A project on plain upstream BMad, whose skill folders are not the verified pinned copy's, shows the reduced-mode notice in place of the look-back action (AD-14); opening an upstream PR for epic-scoped metadata is optional. (CAP-13, CAP-18; AD-12, AD-14; bmad-integration.md Upstream extensions)

## Done when

1. In a project with Retrospectives on, a finished epic is looked back on from the board using only UI chat and buttons, run live with Claude Code, and `epic-<slug>-retrospective.md` exists beside it with its verdict shown on the epic header (CAP-13; E7-R2, E7-R3, E7-R4).
2. A pitfall the retrospective proposes is recorded in `AGENTS.md` and saved from the UI, and the next build dispatched in that project has it in its worktree's `AGENTS.md` (CAP-13; E7-R5).
3. An action item becomes a ticket on the board through an approved ticket session, with no ticket written by Ogden (E7-R6).
4. With Retrospectives off, including every Simple project, no look-back action, offer or verdict shows, a retrospective route is refused with `feature_off`, and nothing is read or written for it (AD-22; E7-R1).
5. A project whose BMad is not the verified pinned copy shows the reduced-mode notice in place of the look-back action (AD-14; E7-R7).
6. The epic's end-to-end suite passes on macOS, Windows and Linux, and it is released in an `ogden-agents` npm version after epic 6's.

## Boundaries

Starting retrospectives and carrying their lessons back. Live checks use Claude Code; because epic 6 ships first, every agent epic 6 supports starts a look-back through its adapter's `skillInvocation` with no code here, and the end-to-end suite runs the look-back against the fake agent only (per-agent checks stay epic 6's). No retrospective logic, scoring or report of Ogden's own, and no editing of `AGENTS.md` or tickets by Ogden: BMad's skills do that through the agent. No automatic or scheduled retrospectives, no headless runs from the UI, no retrospective of a single ticket or an initiative. No in-app viewer for the retrospective file (epic 8, v2): **Open** does what 4.7 decided. Full build session transcripts are not handed to the retrospective; only short build summaries are (user decision 2026-10-02). No Needs you or webhook notification for a finished epic (epic 11 owns notifications). The one commit Ogden makes here is **Save the lessons**; it never pushes.
