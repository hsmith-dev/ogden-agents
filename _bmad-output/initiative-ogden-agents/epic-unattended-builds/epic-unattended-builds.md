# Tickets build themselves safely and wait for your approval

## Description

In a project where the user turned on Unattended builds (epic 10, AD-22; it needs Board), the board gains **Build this story** and **Build all ready**. Ogden picks nothing for the agent: core chooses each ready ticket whose prerequisites are done, within a concurrency limit per project and per install, gives it its own git worktree in the user data folder and a sandbox, and has the forked bmad-loop run `bmad-build-auto` for that one ticket with Claude Code. Each run is a `build` session, so it streams into the same session view, read-only, with a run header, Stop, a maximum run time, and a plain blocked reason with Retry. When a run ends, core checks the result itself (plan status, an independent test re-run, a non-empty diff) before anything shows as ready for review. The review page shows the checks, the review findings and the diff; **Approve and merge** merges the branch locally and is the only path to `done`; **Reject and retry** sends a note and runs it again. Blocked and ready-for-review reach the Needs you group and any configured webhook. Nothing needs a terminal, and runs keep going when the browser closes.

## Outcome

Stories build in parallel and nothing reaches done without approval; CAP-8's and CAP-12's success criteria are the signal, and the spec's Success signal ("clicks Build, watches stories build in parallel, and approves merges, all without opening a terminal") is the demo.

- E5-R1: Unattended builds exist only in a project with the `builds` piece on (which needs `board`, by 10.2's rule). This epic registers `builds` in `SHIPPED_BMAD_PIECES`; every use-case that serves builds (dispatch, stop, retry, apply a saved fix, verify, review, approve, reject, notification settings per project) calls `requireBmadFeature(workspaceId, 'builds')`, every route goes through `bmadPieceRoutes`, and the runner, dispatcher, verifier and notifier do no work for a workspace with it off. With it off there is no Build action, no Runs tab and no `g r`, and builds write nothing into the repo. (CAP-8, CAP-9, CAP-10, CAP-12, CAP-14, CAP-19; AD-22, AD-1)
- E5-R2: Dispatch is core's. **Build this story** dispatches one ticket; **Build all ready** keeps dispatching every ready ticket (prerequisites done, read through `TicketStorePort`) until none is left or the user stops it. Each run names exactly one ticket. A ticket with an unmet prerequisite is never dispatched. A concurrency limit per workspace and one per install are enforced in core; work over the limit waits in a queue the Runs tab shows. (CAP-8; AD-2, AD-10, AD-17; bmad-integration.md "build-auto preconditions"; EXPERIENCE.md Build actions)
- E5-R3: Each run gets its own git worktree through `VcsPort` (adapter `vcs-git`), created under the user data folder, never inside the repo, on its own branch from the main checkout's current branch with a clean tree; it survives a server restart and is removed after a merge or a discard. Paths stay within Windows' limits. While a run is active, `TicketStorePort` reads that ticket's plan from the run's worktree (AD-10); the watcher never scans worktrees. (CAP-8; AD-10, AD-17; Consistency Conventions "Config and data")
- E5-R4: Every unattended run is sandboxed through `SandboxPort`: the agent's native sandbox on this OS (for Claude Code: Seatbelt on macOS, bubblewrap on Linux), then Docker only if it is already installed. With neither, the run is refused with `sandbox_unavailable` and the Build dialog offers the three choices (use another agent, install Docker, build with me watching); "build with me watching" is an attended build session whose every tool call goes through permission cards at the "ask" caution level. Unattended runs never go unsandboxed. (CAP-8; AD-17; spec Constraints; agent-matrix.md "Unattended builds"; EXPERIENCE.md Build actions, Sandbox unavailable, Flow 1 Failure)
- E5-R5: The `buildrunner-bmad-loop` adapter, behind `BuildRunnerPort`, runs the bundled bmad-loop fork through uv (from the bundled wheel) to run `bmad-build-auto` for one named ticket in a given worktree and sandbox with Claude Code, with an allowlisted environment, streams its activity, reports its result from the plan, and stops its whole process tree. Skill names appear only inside this adapter and `tickets-v7` (AD-12). Whatever the fork lacks (running one named v7 ticket headless, a run folder outside the repo, a machine-readable event stream, no multiplexer the user must install) is one patch per upstream PR on the fork's `ogden-agents` branch, tagged, re-vendored with `forks.lock`, and opened upstream. No user installs tmux or psmux by hand. (CAP-8, CAP-9; AD-1, AD-12, AD-13, AD-21; spec Constraints "Reuse BMAD before building"; bmad-integration.md Reuse first, Fork extensions)
- E5-R6: A run streams live: the runner emits the same `session.*` events as a chat, so the build session renders in the session view read-only (no composer), with a run header (ticket, agent, sandbox used, time left before the run limit, outcome) and **Stop** while running. The Runs tab (`g r`, in 10.6's slot) lists every run with its outcome and the queue, and opens the live run view; a sidebar row per build session shows its state. (CAP-9, CAP-17; AD-4, AD-5, AD-8, AD-18; EXPERIENCE.md Live run view, Information Architecture Workspace: Runs)
- E5-R7: A blocked run shows its plain reason and **Retry**. Each `bmad-build-auto` halt maps to a code and the plain sentence in EXPERIENCE.md Voice and Tone, with the raw code under "Show details" (always in Developer mode). Retry marks the plan's resume status through `tickets.py mark`, which clears the blocked fields, and redispatches it in its worktree, so it resumes from the right status. An intent-gap halt also offers **Apply the saved fix and retry** (`git apply` in the worktree, set `in-review`, redispatch). A run past its maximum run time is stopped by core and marked blocked ("Stopped after 45 minutes without finishing."). (CAP-9; AD-8, AD-10, AD-17; bmad-integration.md Plan statuses, build-auto preconditions; EXPERIENCE.md Run `blocked`, Run hit time limit)
- E5-R8: Runs keep going when the browser closes, because the server owns their processes. Quit with runs active says how many and stops them as `stopped` only when confirmed. When the server starts, a run whose process is gone becomes `blocked` with the reason "interrupted" and Retry, its worktree kept. (CAP-8, CAP-9, CAP-17; AD-3, AD-8)
- E5-R9: After every run, core verifies before the UI may show the ticket as ready for review: the plan status is `built`, an independent re-run of the project's tests in the worktree, inside the sandbox, passes, and the diff against the base is not empty. The result is `verified` or `failed` with the failing check named ("3 tests failed when re-run"); a run that claims success but whose tests fail shows as failed. (CAP-10; AD-8, AD-17; EXPERIENCE.md Review, Run `failed` verification)
- E5-R10: The review page (`/w/:wsId/review/:ref`) leads with a plain summary and the three checks, then the review findings from the plan, then the diff behind "Show the code changes (N files)", with a sticky approve bar. **Approve and merge** is disabled until every check passes; it merges the run's branch into the main checkout's branch locally (never a push, never a force), then marks the ticket `done` through `TicketStorePort.mark`, the only path to `done` (AD-10; epic 4's board never offers it). A conflicting merge leaves the main checkout unchanged and blocks the run as needing a rebase, with **Update and retry**. **Reject and retry** takes an optional note to the agent and redispatches. (CAP-12; AD-10, AD-17; EXPERIENCE.md Review, Merge conflict on approve, Flow 1 steps 9 to 11)
- E5-R11: Blocked runs and tickets ready for review appear in the Needs you group across workspaces (with the tab-title count) and are sent through `NotifierPort` to each configured webhook (adapter `notify-webhook`) whose events include them. Settings: Notifications adds a webhook URL, chooses its events (Blocked, Ready for review) and has **Send test** with the HTTP result inline; browser notifications are an opt-in toggle while a tab is open. A webhook URL is treated as a secret (AD-16), and a payload carries no code, diff or secret. (CAP-14; AD-1, AD-16; architecture Deferred "Notification transports beyond webhook"; EXPERIENCE.md Needs you group, Notifications settings, Webhook test failed)
- E5-R12: Unattended builds work on macOS, Windows and Linux. OS-sensitive parts (worktree paths and long paths, stopping a run's process tree, the sandbox chain, bmad-loop's process hosting) are probed in CI on all three before they are built, and on Windows, where Claude Code has no native sandbox, the Docker and attended paths are what users get. (CAP-8, CAP-1; AD-17, AD-21; spec Constraints "runs natively on macOS, Windows, and Linux"; agent-matrix.md)

## Done when

1. In a project with Unattended builds on, two ready, independent tickets build in parallel in their own worktrees without touching each other's files, and a ticket with an unmet prerequisite is not dispatched; with the piece off nothing is offered, nothing is written, and a builds use-case is refused with `feature_off` (CAP-8, AD-17, AD-22; E5-R1 to E5-R5).
2. A run that claims success but whose tests fail is shown as failed (CAP-10; E5-R9).
3. A blocked run shows its reason, and Retry resumes from the right status; a run past its maximum time, or cut off by a server restart, shows as blocked with Retry (CAP-9, AD-3, AD-17; E5-R6 to E5-R8).
4. Approving a built ticket merges it and marks it done, a conflicting merge blocks as needing a rebase, and no other path writes `done` (CAP-12, AD-10, AD-17; E5-R10).
5. With no native sandbox and no Docker, an unattended run is refused with the choices shown; a blocked run and a ticket ready for review each reach a configured webhook (AD-17, CAP-14; E5-R4, E5-R11).
6. The epic's end-to-end suite passes on macOS, Windows and Linux, and it is released in an `ogden-agents` npm version after epic 4's (E5-R12).

## Boundaries

Claude Code builds, sandboxed natively on macOS and Linux, through Docker or attended elsewhere. Other agents' builds are v2 (epic 8; user, 2026-10-02), which adds adapters only: `BuildRunnerPort`, `SandboxPort` and the dispatcher stay agent-neutral. No cost, token or usage tracking and no budget caps (spec Non-goals, AD-8, CAP-11 retired); the maximum run time and the concurrency limits are the only limits. No push to a remote and no pull requests: approve merges locally. The review page shows the diff read-only; line comments and code review in the app are epic 8 (v2). Retrospectives are epic 7. It owns bmad-loop's fork patches and their upstream PRs; epic 4 owns the BMAD-METHOD label patch and the board, which this epic adds Build actions and runs to.
