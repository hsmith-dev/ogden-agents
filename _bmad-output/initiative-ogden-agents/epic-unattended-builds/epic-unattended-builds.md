# One ticket builds safely, and you approve and merge it

## Description

Epic 5a of the two halves of Unattended builds (the second is epic 11, 5b). In a project where the user turned on Unattended builds (epic 10, AD-22; it needs Board), a ticket card on the board gains **Build**. Ogden picks nothing for the agent: core dispatches the ticket when its prerequisites are done, within a concurrency limit per project and per install, gives it its own git worktree in Ogden's data folder and a sandbox, and has the forked bmad-loop run `bmad-build-auto` for that one ticket with Claude Code. Each run is a `build` session, so it streams into the same session view, read-only, with Stop, a maximum run time, and a plain blocked reason with Retry. When a run ends with its plan `built` and a non-empty diff, its ticket is ready for review. The review page shows the checks, the review findings and the diff; **Approve and merge** merges the branch locally and is the only path to `done`; **Reject and retry** sends a note and runs it again. Nothing needs a terminal, and runs keep going when the browser closes. Epic 11 adds the full run view and Runs tab, Build all ready on the board, the independent test re-run, and Needs you and webhooks.

## Outcome

One ticket builds unattended and nothing reaches done without approval; CAP-12's success criterion and the first half of CAP-8's ("a ticket with an unmet prerequisite is not dispatched"; two builds in parallel without touching each other's files) are the signal. The demo: Build on a ready ticket, watch it in the session view, approve, and see it Done on the board.

- E5-R1: Unattended builds exist only in a project with the `builds` piece on (which needs `board`, by 10.2's rule). This epic registers `builds` as available; every use-case that serves builds (dispatch, stop, retry, review, approve, reject, run limits per project) calls `requireBmadFeature(workspaceId, 'builds')`, every route goes through 10.2's piece route helper, and the runner and dispatcher do no work for a workspace with it off. With it off there is no Build action and builds write nothing into the repo. (CAP-8, CAP-9, CAP-12, CAP-19; AD-22, AD-1)
- E5-R2: Dispatch is core's. **Build** on a card dispatches one ticket; core also accepts an all-ready request, which keeps dispatching every ready ticket until none is left or the user stops it (its board button is epic 11's). Each run names exactly one ticket. A ticket with an unmet prerequisite (read through `TicketStorePort`) is never dispatched. A concurrency limit per workspace and one per install are enforced in core, default 2 and 3, editable in Workspace settings and Settings; work over the limit waits in a queue and its card shows Queued. (CAP-8; AD-2, AD-10, AD-17; bmad-integration.md "build-auto preconditions"; EXPERIENCE.md Build actions, Workspace settings)
- E5-R3: Each run gets its own git worktree through `VcsPort` (adapter `vcs-git`), created under Ogden's data folder, never inside the repo, on its own branch from the main checkout's current branch with a clean tree; bmad-loop's run folder is in the data folder too. The worktree survives a server restart and is removed after a merge or a discard. Paths stay within Windows' limits. While a run is active, `TicketStorePort` reads and marks that ticket's plan in the run's worktree (AD-10); the watcher never scans worktrees. (CAP-8; AD-10, AD-17; Consistency Conventions "Config and data")
- E5-R4: Every unattended run is sandboxed through `SandboxPort`: the agent's native sandbox on this OS (for Claude Code: Seatbelt on macOS, bubblewrap on Linux), then Docker only if it is already installed. With neither, the run is refused with `sandbox_unavailable` and the Build dialog offers the three choices (use another agent, install Docker, build with me watching); "build with me watching" is an attended build session whose every tool call goes through permission cards at the "ask" caution level. On Windows, Build defaults to building with the user watching, and Docker Desktop is optional. Unattended runs never go unsandboxed. (CAP-8; AD-17; spec Constraints; agent-matrix.md "Unattended builds"; EXPERIENCE.md Build actions, Sandbox unavailable, Flow 1 Failure)
- E5-R5: The `buildrunner-bmad-loop` adapter, behind `BuildRunnerPort`, runs the bundled bmad-loop fork through uv (from the bundled wheel) to run `bmad-build-auto` for one named ticket in a given worktree and sandbox with Claude Code, with an allowlisted environment, so the agent loads the project's `AGENTS.md` as in the repo; it streams its activity, reports its result from the plan, maps halts to Ogden's blocked codes, and stops its whole process tree. Skill names and the halt mapping appear only inside this adapter and `tickets-v7` (AD-12). Whatever the fork lacks (running one named v7 ticket headless, a run folder outside the repo, a machine-readable event stream, no multiplexer the user must install) is one patch per upstream PR on the fork's `ogden-agents` branch, tagged, re-vendored with `forks.lock`, and opened upstream. No user installs tmux or psmux by hand. (CAP-8, CAP-9; AD-1, AD-12, AD-13, AD-21; spec Constraints "Reuse BMAD before building"; bmad-integration.md Reuse first, Fork extensions)
- E5-R6: A run streams live: the runner emits the same `session.*` events as a chat, so the build session renders in the session view read-only (no composer), with a header naming the ticket and outcome and **Stop** while running; the epic 2 sidebar lists it like any session. (CAP-9 first part; AD-4, AD-5, AD-8, AD-18)
- E5-R7: A blocked run shows its plain reason and **Retry** in its header. Retry marks the plan's resume status through `tickets.py mark` in the run's worktree, which clears the blocked fields, and redispatches it there, so it resumes from the right status. A run past its maximum run time (default 45 minutes, editable in Settings) is stopped by core and marked blocked ("Stopped after 45 minutes without finishing."). (CAP-9; AD-8, AD-10, AD-17; bmad-integration.md Plan statuses; EXPERIENCE.md Run `blocked`, Run hit time limit)
- E5-R8: Runs keep going when the browser closes, because the server owns their processes. Quit with runs active says how many, and on confirmation stops them and marks them `blocked` with the reason "interrupted"; when the server starts after a crash or reboot, a run whose process is gone gets the same, its worktree kept. Retry is by hand. Turning Unattended builds (or Board) off lets active runs finish and dispatches nothing new. (CAP-8, CAP-9, CAP-17; AD-3, AD-8, AD-22)
- E5-R9: When a run ends, core checks before the ticket shows as ready for review that the plan status is `built` and the diff against the base is not empty (epic 11 adds the independent test re-run). The review page (`/w/:wsId/review/:ref`) leads with a plain summary and the checks, then the review findings from the plan, then the diff behind "Show the code changes (N files)", with a sticky approve bar. **Approve and merge** is disabled until every check passes; it merges the run's branch into the branch the main checkout has checked out, locally (never a push, never a force), is refused while that checkout has uncommitted changes, then marks the ticket `done` through `TicketStorePort.mark`, the only path to `done` (AD-10; epic 4's board never offers it). A conflicting merge leaves the main checkout unchanged and blocks the run as needing a rebase, with **Update and retry**. **Reject and retry** takes an optional note to the agent and redispatches. (CAP-12; AD-10, AD-17; EXPERIENCE.md Review, Merge conflict on approve, Flow 1 steps 9 to 11)
- E5-R10: Builds work on macOS, Windows and Linux. OS-sensitive parts (worktree paths and long paths, stopping a run's process tree, the sandbox chain, bmad-loop's process hosting) are probed in CI on all three before they are built, and on Windows, where Claude Code has no native sandbox, the attended and Docker paths are what users get. (CAP-8, CAP-1; AD-17, AD-21; spec Constraints "runs natively on macOS, Windows, and Linux"; agent-matrix.md)

## Done when

1. In a project with Unattended builds on, two ready, independent tickets built one at a time from their cards run in parallel in their own worktrees without touching each other's files, and a ticket with an unmet prerequisite is not dispatched; with the piece off nothing is offered, nothing is written, and a builds use-case is refused with `feature_off` (CAP-8, AD-17, AD-22; E5-R1 to E5-R5).
2. A blocked run shows its reason, and Retry resumes from the right status; a run past its maximum time, or cut off by Quit or a restart, shows as blocked with Retry (CAP-9, AD-3, AD-17; E5-R6 to E5-R8).
3. Approving a built ticket merges it locally and marks it done, approve is refused on a dirty checkout, a conflicting merge blocks as needing a rebase, and no other path writes `done` (CAP-12, AD-10, AD-17; E5-R9).
4. With no native sandbox and no Docker, an unattended run is refused with the choices shown, and on Windows the attended build works (AD-17; E5-R4, E5-R10).
5. The epic's end-to-end suite passes on macOS, Windows and Linux, and it is released in an `ogden-agents` npm version after epic 4's (E5-R10).

## Boundaries

Claude Code builds, sandboxed natively on macOS and Linux, through Docker or attended elsewhere. Other agents' build profiles and sandboxes are epic 6, which adds adapters only: `BuildRunnerPort`, `SandboxPort`, the run's `agent` field and the dispatcher stay agent-neutral. The full run view, the Runs tab, Build all ready on the board, the independent test re-run, and Needs you and webhook notifications are epic 11 (5b). No cost, token or usage tracking and no budget caps (spec Non-goals, AD-8, CAP-11 retired); the maximum run time and the concurrency limits are the only limits. No push to a remote and no pull requests: approve merges locally. The review page shows the diff read-only; line comments and code review in the app are epic 8 (v2). Retrospectives are epic 7. It owns bmad-loop's fork patches and their upstream PRs; epic 4 owns the BMAD-METHOD label patch and the board, which this epic adds Build to.
