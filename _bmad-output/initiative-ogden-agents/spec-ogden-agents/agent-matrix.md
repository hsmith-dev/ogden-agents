## How the UI uses it

- **Permission cards (CAP-4):** ACP `session/request_permission` with option kinds `allow_once`, `allow_always`, `reject_once`, `reject_always`. "Always allow" rules are stored and enforced by Ogden Agents' core, never handed to the agent as `allow_always` (user decision, 2026-09-30).
- **Permission modes (CAP-4, CAP-5; 2026-10-02):** each chat runs in Ask, Auto or Skip all, and an agent declares which it offers (`AgentPort.permissionModes`). Claude Code (claude-agent-acp 0.84.0) lists ACP session modes `default` (Manual), `acceptEdits`, `plan`, `auto` and `bypassPermissions` (the last only when not running as root outside a sandbox and not disabled by settings) and supports `session/set_mode`: Ask is `default`, Auto `auto`, Skip all `bypassPermissions`. A new ACP session starts in the user's or project's `permissions.defaultMode`, so core sets the chat's mode on every start and reopen before the first prompt. When the model lacks Auto the adapter falls back to `acceptEdits` and reports it (`current_mode_update`); any mode the chat didn't choose moves it to Ask, and the agent is told Ask when that mode asks less. The plan-exit card offers its mode-raising options as `allow_always`; Ogden only ever selects `allow_once`/`reject_once`. In `bypassPermissions` Claude Code skips its checks before asking; a request that still arrives is one of its own safety checks and shows a card with no Always allow. Its terminal starts with `--permission-mode default|auto` or `--dangerously-skip-permissions`. Auto keeps protected files guarded (user decision 2026-10-02): Auto sessions start with `permissions.ask` rules (`Edit(**/.claude/**)`, `Edit(**/CLAUDE.md)`, …) in `_meta.claudeCode.options.settings` (the CLI's flag-settings tier; ask rules make it call `canUseTool` even in auto, and are bypass-immune, so Skip-all sessions start without them), and the terminal in Auto gets the same rules as `--settings`. They can't be changed once a session runs, so a move into or out of Auto restarts it (resumed). Codex and Gemini modes come with epic 6.
- **Send now or wait (CAP-3; 2026-10-04):** a message sent right away while a turn runs goes in the agent's best declared style (`AgentDescriptor.sendNow`). Claude Code (claude-agent-acp 0.84.0) is `inject`: it implements the `_session/steering` extension request, advertised as `InitializeResponse._meta.steering.supported`, which pushes the message into the running turn (priority `now` pre-empts the current generation, `later` while a permission or elicitation waits) and answers `injected`; the running `session/prompt` settles only once a result answers it. With `_meta.steering.idleBehavior: "promptRequired"` and no turn running it answers `promptRequired` and starts nothing (Ogden always sends that). A second `session/prompt` during a turn is queued by the adapter itself; Ogden never sends one. Antigravity (antigravity-acp 1.3.0) advertises no steering: `interrupt`, which is `session/cancel` and the message sent as the next prompt. Ogden injects only when the descriptor says `inject` and the agent advertised it at `initialize`; otherwise, or when the steer fails or is not answered in 10 s, it interrupts.
- **Resume (CAP-3):** try ACP `session/resume` when advertised, else `session/load`, else start a new session primed from Ogden Agents' stored transcript, marked "Resumed from history". The two-agent resume proof is epic 6's (user decision, 2026-09-30): with Claude Code and Antigravity on a go, v2 (epic 8) on a no-go (2026-10-02).
- **Terminal toggle (CAP-5):** only where the ACP session id is the CLI's own resumable id (Claude Code in v1; Codex in v2; Antigravity only if epic 6's spike shows it). Whether the toggle is offered for a session is `GET` session's `terminal`, from `packages/server/src/terminal-availability.ts` (story 3.7): the same checks, in the same order, as core's switch refusal, each with a plain reason the toggle shows as its tooltip:
  1. `agent_unsupported`: the agent has no terminal resume (no `terminalResume` on its adapter);
  2. `pty_unavailable`: no terminal on this computer (`node-pty` failed to load, AD-19);
  3. `no_agent_session`: the chat has never reached its agent, so there is nothing to resume;
  4. `cli_not_found`: the agent's CLI can't be found.

  Not being idle is not a code: the UI reads the session's state.
- **Unattended builds:** the sandbox decision runs in this order:
  1. the agent's native sandbox on this OS;
  2. Docker, if it is already installed;
  3. otherwise, unattended mode is off for that agent, and the UI offers installing Docker or attended mode (another agent too in v2, when there is one that can build; 2026-10-02).

  Unattended runs never go unsandboxed.
- **Sign-in (CAP-16):** terminal-type auth methods (Claude Code) run in a hidden PTY driven by the UI, with `clientCapabilities.auth.terminal` advertised; other agents use ACP `authenticate` or their CLI login. API keys come from the keychain (`SecretStorePort`, AD-16) and are passed only in the child process environment.
- **Permission modes (CAP-4, 2026-10-02):** each agent declares the per-chat modes it supports (Ask, Auto, Skip all; the standalone permission modes story defines all three for Claude Code). Antigravity declares a mode only where its own ACP mode means the same (third-party reports name `default`, `auto-edit` and `yolo`; verify in 6.1).
