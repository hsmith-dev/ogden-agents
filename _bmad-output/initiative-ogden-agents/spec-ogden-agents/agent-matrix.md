## How the UI uses it

- **Permission cards (CAP-4):** ACP `session/request_permission` with option kinds `allow_once`, `allow_always`, `reject_once`, `reject_always`. "Always allow" rules are stored and enforced by Ogden Agents' core, never handed to the agent as `allow_always` (user decision, 2026-09-30).
- **Permission modes (CAP-4, CAP-5; 2026-10-02):** each chat runs in Ask, Auto or Skip all, and an agent declares which it offers (`AgentPort.permissionModes`). Claude Code (claude-agent-acp 0.84.0) lists ACP session modes `default` (Manual), `acceptEdits`, `plan`, `auto` and `bypassPermissions` (the last only when not running as root outside a sandbox and not disabled by settings) and supports `session/set_mode`: Ask is `default`, Auto `auto`, Skip all `bypassPermissions`. A new ACP session starts in the user's or project's `permissions.defaultMode`, so core sets the chat's mode on every start and reopen before the first prompt. When the model lacks Auto the adapter falls back to `acceptEdits` and reports it (`current_mode_update`); any mode the chat didn't choose moves it to Ask, and the agent is told Ask when that mode asks less. The plan-exit card offers its mode-raising options as `allow_always`; Ogden only ever selects `allow_once`/`reject_once`. In `bypassPermissions` Claude Code skips its checks before asking; a request that still arrives is one of its own safety checks and shows a card with no Always allow. Its terminal starts with `--permission-mode default|auto` or `--dangerously-skip-permissions`. Auto keeps protected files guarded (user decision 2026-10-02): Auto sessions start with `permissions.ask` rules (`Edit(**/.claude/**)`, `Edit(**/CLAUDE.md)`, …) in `_meta.claudeCode.options.settings` (the CLI's flag-settings tier; ask rules make it call `canUseTool` even in auto, and are bypass-immune, so Skip-all sessions start without them), and the terminal in Auto gets the same rules as `--settings`. They can't be changed once a session runs, so a move into or out of Auto restarts it (resumed). Codex and Gemini modes come with epic 6.
- **Models (CAP-3; story 11, 2026-10-04):** each chat runs on a model the user can switch, and agents expose models agent-neutrally. Claude Code (claude-agent-acp 0.84.0 on @agentclientprotocol/sdk 1.5.1) lists them as an ACP session config option (`configOptions`, id `model`, category `model`, `type: select`, with `default` and aliases such as `opus`, `sonnet`, `haiku` and `[1m]` variants, filtered by the user's `availableModels` and managed `deniedModels`) in `session/new`, `session/resume` and `session/load`, switches a running session with `session/set_config_option` (it calls the SDK's `setModel`), refuses an unlisted value, and may publish `config_option_update`; its own start model is `ANTHROPIC_MODEL`, then `settings.model`, then a resumed session's. SDK 1.5.1 has no `session/set_model`; Ogden uses only the stable config-option path and never sets `ANTHROPIC_MODEL`. Its terminal takes `--model`. Antigravity (antigravity-acp 1.3.0, spike 6.1) answers `session/new` with `configOptions` `model` (14 Gemini models) and the older `models` field; switching it with `session/set_config_option` is a live check. Codex's adapter (spike 12.1) lists a `model` config option; Grok (spike 12.2) advertises a model list in its `_meta` extensions, so it may need the descriptor's static list (`AgentDescriptor.models`, applied at spawn as a variable or flag; switching restarts the agent, resumed).
- **Send now or wait (CAP-3; 2026-10-04):** a message sent right away while a turn runs goes in the agent's best declared style (`AgentDescriptor.sendNow`). Claude Code (claude-agent-acp 0.84.0) is `inject`: it implements the `_session/steering` extension request, advertised as `InitializeResponse._meta.steering.supported`, which pushes the message into the running turn (priority `now` pre-empts the current generation, `later` while a permission or elicitation waits) and answers `injected`; the running `session/prompt` settles only once a result answers it. With `_meta.steering.idleBehavior: "promptRequired"` and no turn running it answers `promptRequired` and starts nothing (Ogden always sends that). A second `session/prompt` during a turn is queued by the adapter itself; Ogden never sends one. Antigravity (antigravity-acp 1.3.0) advertises no steering: `interrupt`, which is `session/cancel` and the message sent as the next prompt. Ogden injects only when the descriptor says `inject` and the agent advertised it at `initialize`; otherwise, or when the steer fails or is not answered in 10 s, it interrupts.
- **Resume (CAP-3):** try ACP `session/resume` when advertised, else `session/load`, else start a new session primed from Ogden Agents' stored transcript, marked "Resumed from history". The two-agent resume proof is epic 6's (user decision, 2026-09-30): with Claude Code and Antigravity on a go, v2 (epic 8) on a no-go (2026-10-02).

- **Terminal toggle (CAP-5):** only where the ACP session id is the CLI's own resumable id (Claude Code in v1; Antigravity only if epic 6's spike shows it; Codex and Grok in v1.1 only if their live checks show it). Whether the toggle is offered for a session is `GET` session's `terminal`, from `packages/server/src/terminal-availability.ts` (story 3.7): the same checks, in the same order, as core's switch refusal, each with a plain reason the toggle shows as its tooltip:
  1. `agent_unsupported`: the agent has no terminal resume (no `terminalResume` on its adapter);
  2. `pty_unavailable`: no terminal on this computer (`node-pty` failed to load, AD-19);
  3. `no_agent_session`: the chat has never reached its agent, so there is nothing to resume;
  4. `cli_not_found`: the agent's CLI can't be found.

  Not being idle is not a code: the UI reads the session's state.
- **Usage limits and handoff (CAP-3, CAP-15; 2026-10-04):** each descriptor lists `usageLimitPatterns`, tested only against the agent's own error text when a prompt fails; a match is error code `usage_limit` and the chat offers to continue with another agent. Claude Code: "usage limit reached", "5-hour/weekly … limit reached", "you've hit your limit". Antigravity: `RESOURCE_EXHAUSTED`, "quota exceeded/exhausted", "exhausted your capacity/quota". A short API rate limit (a 429 that clears in seconds) is left an ordinary error: Try again fits it better than another provider. Unverified against live limits: the release's live check confirms them. Handoff brief budgets: Claude Code 100,000 characters, Antigravity 150,000.
- **Unattended builds:** the sandbox decision runs in this order:
  1. the agent's native sandbox on this OS;
  2. Docker, if it is already installed;
  3. otherwise, unattended mode is off for that agent, and the UI offers installing Docker or attended mode (another agent too in v2, when there is one that can build; 2026-10-02).

  Unattended runs never go unsandboxed.
- **Sign-in (CAP-16):** terminal-type auth methods (Claude Code) run in a hidden PTY driven by the UI, with `clientCapabilities.auth.terminal` advertised; other agents use ACP `authenticate` or their CLI login. API keys come from the keychain (`SecretStorePort`, AD-16) and are passed only in the child process environment.
- **Permission modes (CAP-4, 2026-10-02):** each agent declares the per-chat modes it supports (Ask, Auto, Skip all; the standalone permission modes story defines all three for Claude Code). Antigravity declares a mode only where its own ACP mode means the same (third-party reports name `default`, `auto-edit` and `yolo`; verify in 6.1).

## Remote machines (CAP-24, epic 19; single machine, AD-24/25/26)

Choosing a confirmed remote machine as a chat or build target is wired for the first time in story 19.7 (epic 19 stories 19.1-19.6 built the mechanism — registry, credentials, push/pull, SSH spawn — but nothing before 19.7 constructed the real capability or exposed a REST field for it). What's eligible, and what isn't, follows directly from `acp-base`'s own shared ACP client above:

- **Chat is remote-eligible for every agent in this matrix**, with no per-agent exception: every one of them, Claude Code included, runs through `acp-base`'s `createAcpAgent`/`startOnChild` (the section at the top of this file), and `spawnAcpProcess` (story 19.7's refactor sweep moved it, unchanged, into `process-launch.ts`) spawns the exact same `AcpLaunch` either locally or, when a connection is given, over SSH via `RemoteHostChannel`'s `exec`. The adapter layer never asks which; a remote chat looks identical to a local one in every event the UI shows.
- **Builds are remote-eligible only in `attended` mode** (19.6's own scope decision, unchanged by this story): an unattended build on a remote machine is refused outright, before anything is written, with `UNATTENDED_REMOTE_MESSAGE`'s plain text (`packages/shared/src/builds.ts`, re-exported unchanged from `packages/core/src/build-names.ts` so the web layer's `MachinePicker`/`build-dialog.tsx` can show the exact same words without depending on core). This is not a per-agent limitation like the rows above — it applies to every agent, because the scope decision is about the *sandbox* (unattended needs one; a remote machine's own sandbox is out of scope for CAP-24), not about any one agent's own capability.
- **A plain chat's remote `cwd` is the machine's own home directory** (`REMOTE_CHAT_CWD = '.'`, `packages/core/src/chat/constants.ts`; this story's own design call, Design Notes): a chat has no pushed worktree the way a build does (CAP-24's non-goals rule out provisioning anything on the remote), so it runs in the one folder every confirmed machine is guaranteed to have, never a path Ogden Agents invented.

Caveats carried over from 19.4/19.5, worth stating here rather than only in code comments (both are known, accepted gaps, not open design questions):

- **POSIX shell and `git` on `PATH` are assumed** on the remote machine (`remote-worktree-sync.ts`'s own header): a build's push/pull scripts, and a chat or build's `cd … && exec …` launch line (`buildRemoteCommand`), both need a POSIX-compatible default shell. A remote whose default shell isn't POSIX-compatible is out of this epic's automated tests, the same posture as story 19.2's untested Windows keychain fallback.
- **`sshd`'s own `AcceptEnv`/`SetEnv` can silently drop an env var** the agent's process needs (story 19.5's own flagged gap): env vars (an agent's API key included, AD-16) travel only through SSH's protocol-level `exec` env option, never spliced into the command line — but many `sshd` configs restrict which names they'll accept and drop the rest without telling the client. A real remote machine whose `sshd` doesn't forward the needed variable fails loudly (`agent_unavailable`, or a sign-in-required refusal), never a silent fallback and never a leaked secret on a command line.

## Terminal panes (epic 16, Developer mode)

Each agent's own CLI can run in a terminal pane, found by detection and never installed by Ogden Agents (the user installs it, then presses Detect). The user signs in inside the CLI; Ogden Agents never sees or stores that sign in, and passes the pane no key or token. A pane starts the program by the absolute path detection found, with no flag of Ogden Agents' own that skips a permission prompt. The names and places below come from each vendor's public docs and the spike 16.1 findings; the user's live checks on a Mac and a Windows machine confirm each.
